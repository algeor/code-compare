+## Context
+
+The Handler Orchestrator evaluates `FaultHandler` CRs against an inspection's failure signal through three gates: Level 1 (active status), Level 2 (infrastructure filter), Level 3 (failure matching). Level 3 uses `match_stages` / `match_pipeline` from `applicability.py`, which currently evaluates `stage_name` (fnmatch) and `log_contains` (regex against full stage/pipeline log fetched from HDLF via `InspectionReader`).
+
+The `FailureMatch` model already has a `relevance: str | None` field in `fl_shared/cr_models.py` — a plain-language description of the failures the handler addresses. It has never been evaluated. A `TODO` comment in `applicability.py` marks the gap.
+
+This design builds on PR PIPELINE3-1446 (regex log matching), which introduces `InspectionReader` into the orchestrator, `_prefetch_logs`, the OR-across-entries semantics, and the `HandlerEvalResult` return type. That PR must be merged before this work begins.
+
+The orchestrator calls `ai_hub.py` (`sap_ai_hub_chat_structured`) for other LLM-based decisions (e.g. WIP detection gate). The same path is used here — no new credential or auth path is introduced.
+
+## Goals / Non-Goals
+
+**Goals:**
+- Evaluate `relevance` using an LLM when `log_contains` does not produce a definitive match
+- Keep all relevance judgements for one inspection to a single LLM call
+- Record every LLM-driven decision in the audit trail with a machine-readable reason
+- Fail closed on LLM error — handlers pending LLM evaluation are excluded, not included
+- Leave handlers with no `relevance` fields completely unaffected
+
+**Non-Goals:**
+- Tool use or MCP access for the LLM — the orchestrator uses `InspectionReader` directly (consistent with PR PIPELINE3-1446)
+- Changing `stage_name` matching logic — out of scope
+- Supporting `relevance` evaluation in the handler controller validator — out of scope for this change
+- Changing the `pipeline_data` MCP transport
+
+## Decisions
+
+### OR semantics with regex priority (not AND)
+
+The `log_contains` and `relevance` fields within an entry are evaluated with OR semantics and short-circuit on regex match:
+
+1. `log_contains` present and matches → entry matches immediately, no LLM call
+2. `log_contains` present but no match, `relevance` set → ask LLM
+3. `log_contains` absent, `relevance` set → ask LLM
+4. Neither field set → no match (empty entry is meaningless; validator already rejects these)
+
+**Rationale:** The manager explicitly chose OR with regex priority. `log_contains` is a cheap, deterministic fast-track. The LLM is a safety net for failures the regex did not anticipate — not a redundant confirmation of what the regex already confirmed.
+
+**Alternative considered:** AND semantics (Jira wording). Rejected — would mean the LLM is only invoked when the regex already matched, which is backwards: you'd spend LLM tokens on the easy cases and skip the hard ones.
+
+### Single batched LLM call per inspection
+
+All `(failure_excerpt, relevance_description)` pairs that need LLM evaluation across all handlers are collected and sent in one `sap_ai_hub_chat_structured` call.
+
+**Rationale:** Keeps latency and token cost proportional to the number of failed stages, not the number of handlers. For N failed stages and M handlers with relevance, the prompt contains at most N×M pairs — but in practice most handlers will either match via regex or be filtered by `stage_name`, so the actual pairs are much fewer.
+
+**Alternative considered:** One call per handler. Rejected — violates the Jira batching requirement and increases latency linearly with handler count.
+
+### Failure excerpt extraction, not full log
+
+Before passing stage content to the LLM, the orchestrator extracts a compact failure excerpt from the stage log: unique error/fatal/exception lines from the head of the log, plus the last N lines as context. This mirrors the `_format_truncated` logic in `pipeline_data_mcp.py`.
+
+**Rationale:** Full stage logs can be thousands of lines. Passing them all to the LLM risks context overflow and increases token cost dramatically. The failure excerpt contains the signal the LLM needs without the noise.
+
+**Extraction utility:** Implemented in `relevance_evaluator.py`. Shares the same logic as the MCP but is not coupled to it — no import dependency on `fl_mcp_servers`.
+
+### Fail closed on LLM error
+
+If `evaluate_relevance_batch()` raises `RelevanceEvalError`, all handlers that were pending LLM evaluation receive a `filtered_log_match` decision with `reason: "relevance_eval_failed"`.
+
+**Rationale:** Fail open would silently degrade to pre-feature behaviour, which is unobservable. Fail closed makes the LLM dependency visible in the audit trail and prevents handlers from being activated on a failure mode they might not address.
+
+**Alternative considered:** Fail open (mechanical fallback). Rejected — harder to observe and diagnose; the audit trail would show a match with no indication that the LLM was skipped.
+
+### Two-pass orchestrator structure
+
+`evaluate()` in `orchestrator.py` runs two passes:
+
+- **Pass 1** (mechanical): all handlers evaluated via `_evaluate_handler`. Outcome: matched, rejected, or `relevance_candidates` populated.
+- **Pass 2** (LLM): only runs if any handlers have `relevance_candidates`. One batch call. Verdicts applied. Handlers move to matched or rejected.
+
+`select_versions()` and `OrchestrationResult` construction are untouched — they receive the same `candidates` list as before.
+
+**Rationale:** Cleanly separates concerns. The mechanical pass is deterministic and fast; the LLM pass is the optional, expensive step. All existing logic below `select_versions` is unchanged.
+
+### `_stage_needs_relevance` / `_pipeline_needs_relevance` as separate helpers
+
+Rather than changing `_stage_matches_any` to a tri-state, two new boolean helpers are added to `applicability.py`:
+
+- `_stage_needs_relevance(criteria_list, stage, stage_logs) -> bool`
+- `_pipeline_needs_relevance(criteria_list, pipeline_log) -> bool`
+
+These return `True` when no entry matched mechanically, but at least one surviving entry (i.e. not eliminated by `stage_name`) has `relevance` set.
+
+**Rationale:** Keeps `_stage_matches_any` unchanged and single-purpose. The two functions are called in sequence in `_evaluate_handler` — if `_stage_matches_any` returns `True`, `_stage_needs_relevance` is never called.
+
+### `HandlerEvalResult.relevance_candidates`
+
+`HandlerEvalResult` (introduced by PR PIPELINE3-1446) gains one new field: `relevance_candidates: list[RelevanceCandidate]`. When non-empty, `is_matched=False` and `rejection=None` — the handler's fate is not yet decided.
+
+`RelevanceCandidate` is a small Pydantic model in `models.py` carrying: `stage_id` (or `None` for pipeline_scoped), `stage_name`, `failure_excerpt`, and `relevance_description`.
+
+**Rationale:** `HandlerEvalResult` is purely internal to the orchestrator — it is never serialized, persisted, or returned to callers. Safe to extend. Keeping the candidates on the result object rather than a parallel data structure keeps `_evaluate_handler` self-contained.
+
+## Risks / Trade-offs
+
+- **LLM latency added to orchestration critical path** → Mitigated by batching (one call regardless of handler count) and by the regex short-circuit (many handlers will never reach the LLM). The LLM call only runs when at least one handler has `relevance` set and its regex didn't match.
+- **LLM cost proportional to inspection failure count** → Acceptable — the excerpt extraction caps the per-stage token contribution. An inspection with 5 failed stages and 3 handlers with relevance produces a small prompt.
+- **LLM verdict quality depends on excerpt quality** → The failure excerpt must faithfully represent the failure. The extraction logic should prefer lines containing error/fatal/exception keywords and include the log tail as context. Edge cases (e.g. failures with no error-keyword lines) fall back to the tail only — still better than nothing.
+- **Breaking change for entries with only `stage_name` set** → Entries with `stage_name` but no `log_contains` and no `relevance` will now not match. The handler controller validator already warns that at least one of the three fields should be set; in practice no deployed CR has this pattern (confirmed by inspection of the handlers registry).
+
+## Migration Plan
+
+No database migrations required. No API changes. The feature is additive:
+
+1. Merge PR PIPELINE3-1446 first.
+2. Deploy this change. Handlers without `relevance` fields are unaffected — the new code path is never entered.
+3. Handler authors add `relevance` fields to their CRs incrementally. Each CR update is independently safe.
+4. Rollback: revert the deployment. No state is persisted by the new code path.
+

+

+- **LLM prompt wording**: The prompt structure for the batch call needs to be finalised during implementation and reviewed for clarity and correctness.

+## ADDED Requirements
+
+### Requirement: Relevance evaluation via LLM
+The orchestrator SHALL evaluate a handler's `relevance` field using an LLM when mechanical matching (`log_contains`) does not produce a definitive result for any match entry. The LLM receives a compact failure excerpt extracted from the stage or pipeline log, not the full log.
+
+#### Scenario: Relevance-only entry matches stage_scoped handler
+- **WHEN** a `stage_scoped` handler has a match entry with `relevance` set and no `log_contains`, and the failure excerpt for a failed stage semantically matches the relevance description
+- **THEN** the handler appears in `OrchestrationResult.handlers` with an `ApplicabilityDecision` with `result: "matched"`
+
+#### Scenario: Relevance-only entry matches pipeline_scoped handler
+- **WHEN** a `pipeline_scoped` handler has a match entry with `relevance` set and no `log_contains`, and the pipeline failure excerpt semantically matches the relevance description
+- **THEN** the handler appears in `OrchestrationResult.handlers` with an `ApplicabilityDecision` with `result: "matched"`
+
+#### Scenario: Relevance does not match
+- **WHEN** a handler has a match entry with `relevance` set and the LLM verdict is negative
+- **THEN** the handler is excluded with `result: "filtered_log_match"` and a reason that identifies the LLM verdict
+
+#### Scenario: log_contains matches, no LLM call
+- **WHEN** a handler has a match entry with both `log_contains` and `relevance` set, and `log_contains` matches the stage log
+- **THEN** the handler is included immediately and no LLM call is issued for that entry
+
+#### Scenario: log_contains does not match, relevance present, LLM decides
+- **WHEN** a handler has a match entry with both `log_contains` and `relevance` set, and `log_contains` does not match the stage log
+- **THEN** the LLM is asked to evaluate `relevance` and the verdict determines the outcome
+
+#### Scenario: No relevance on any entry
+- **WHEN** all match entries for a handler have no `relevance` field
+- **THEN** no LLM call is issued and matching behaviour is identical to the pre-change implementation
+
+### Requirement: Batched LLM evaluation
+The orchestrator SHALL produce all relevance judgements for one inspection in a single LLM call (or minimum calls dictated by token limits), not one call per handler.
+
+#### Scenario: Multiple handlers with relevance produce one LLM call
+- **WHEN** multiple handlers have match entries with `relevance` set and none matched via `log_contains`
+- **THEN** all relevance judgements are produced in a single LLM call
+
+### Requirement: LLM failure policy
+When the LLM call fails (timeout, upstream error, or malformed response), the orchestrator SHALL apply fail-closed policy: each handler pending LLM evaluation is excluded with `result: "filtered_log_match"` and `reason: "relevance_eval_failed"`.
+
+#### Scenario: LLM failure excludes pending handlers
+- **WHEN** the LLM call raises an error
+- **THEN** every handler that was pending relevance evaluation receives `result: "filtered_log_match"` with `reason: "relevance_eval_failed"`
+
+#### Scenario: LLM failure does not affect mechanically matched handlers
+- **WHEN** the LLM call fails and some handlers already matched via `log_contains`
+- **THEN** those handlers are unaffected and still appear in `OrchestrationResult.handlers`
