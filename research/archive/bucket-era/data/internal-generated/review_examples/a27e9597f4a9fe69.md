-## Summary
-

-### CR-01: `_job_status` crashes with `AttributeError` when `job.status` is `None`
-
-**File:** `fl_control_plane/execution_engine/dispatcher.py:206`
-
-**Issue:** The Kubernetes Python client returns a `V1Job` whose `.status` attribute is `None` until the control plane has processed the newly-created job. -```python

-```

-        return None

-### CR-02: RBAC Role grants handler pods read/patch access to ALL ConfigMaps in the namespace
-
-**File:** `fl_control_plane/execution_engine/rbac.py:48-55`
-
-**Issue:** The Role created by `_ensure_role` grants `get` and `patch` on `configmaps` with no `resourceNames` restriction. Every handler pod running as `fl-execution-agent` can therefore read or patch any ConfigMap in the namespace — including those owned by other services, other pipelines, or Kubernetes system components. In a shared namespace this is a lateral-movement vector: a compromised or misbehaving pod can exfiltrate or corrupt configuration data that belongs to unrelated workloads.
-
-Each agent pod already knows its own ConfigMap name via the `TASK_ID` env var, so it does not need namespace-wide access.
-
-**Fix:** Restrict the role to only ConfigMaps matching the `fl.sap.com/run-id` label, or use `resourceNames` if the names are known at provisioning time. The cleanest approach is a per-execution Role with an exact `resourceNames` entry:
-
-```python
-# in _ensure_role, pass resource_names so each pod can only touch its own CM
-client.V1PolicyRule(
-    api_groups=[""],
-    resources=["configmaps"],
-    resource_names=[f"fl-cm-{short_execution_id}"],  # scoped to this execution
-    verbs=["get", "patch"],
-)
-```
-
-If a single shared role is preferred, scoping by label requires an admission webhook or OPA policy rather than a native RBAC rule. At minimum, document the accepted blast radius and add a comment explaining why namespace-wide access is required.

-### WR-05: `_wait_for_job` has no upper bound — can block the calling thread indefinitely on infrastructure failures
-
-**File:** `fl_control_plane/execution_engine/dispatcher.py:215-221`
-
-**Issue:** `_wait_for_job` loops forever calling `read_namespaced_job`. If the Kubernetes API server becomes unreachable, the `read_namespaced_job` call blocks until a default TCP timeout (which can be minutes), then the loop retries immediately, blocking again. No `_request_timeout` is passed to the API call, and there is no circuit-breaker or wall-clock deadline. Since `run()` uses `executor.map(_wait_for_job, findings)`, a hung poll blocks the thread until the job's `active_deadline_seconds` (up to 3600 s) eventually produces a terminal condition — assuming k8s connectivity resumes.
-
-**Fix:** Pass a request timeout to each API call and optionally add a wall-clock deadline:
-```python
-def _wait_for_job(finding: HandlerFinding) -> HandlerFinding:
-    """Poll until the job reaches a terminal state, then return finding with status set."""
-    while True:
-        status = _job_status(finding.job_name)

-            return finding.model_copy(update={"status": status})

+## Context
+
+FL uses structlog throughout most of `fl_control_plane`, but the logging infrastructure has three problems:
+
+1. **No unified context binding** — `inspection_id` is passed as an explicit keyword argument on every individual `log.*` call. Helper functions called from activities cannot carry `inspection_id` in their log output because they don't receive it as a parameter. This means a significant portion of log lines emitted during an inspection run are invisible when filtering by `inspection_id` in CLS.
+
+2. **stdlib leakage** — Five `fl_control_plane` files use `logging.getLogger(__name__)` (Python stdlib). Stdlib loggers bypass structlog's context pipeline entirely. Even if `bound_contextvars` were used at entry points, these loggers would not pick up the `inspection_id` from context.
+
+3. **`log_config.py` is siloed in `fl_control_plane`** — `engineering_agent`, `finalizer_agent`, and `fl_mcp_servers` have no access to the shared logging setup, so they either skip structured logging or duplicate configuration.
+
+Structlog already has `merge_contextvars` as the first processor in `_SHARED_PROCESSORS` inside `log_config.py`. The plumbing is in place — the only missing piece is consistently using `bound_contextvars` at entry points and ensuring all loggers flow through structlog.
+
+## Goals / Non-Goals
+
+**Goals:**
+- Every log line emitted during an inspection run carries `inspection_id`, visible in CLS when filtering by that ID
+- All FL packages use a single shared `configure_logging()` entry point from `fl_shared`
+- All log calls use structlog — no stdlib `logging.getLogger` in application code
+- Context binding happens once at the entry point of each inspection-scoped operation; helper functions log normally without needing to know about `inspection_id`
+- Non-inspection-scoped code (worker startup, handler controller, infrastructure) uses structlog but no `inspection_scope`
+
+**Non-Goals:**
+- Changing log message content, log levels, or structured field names beyond removing now-redundant `inspection_id=` per-call kwargs
+- Adding new log statements
+- Changing `handler_controller/logging.py` — it is a k8s operator component with no inspection concept and its own formatter; it is out of scope
+- Modifying the CLS pipeline or dashboard configuration
+
+## Decisions
+
+### D1: `inspection_scope` as a context manager in `fl_shared`, not an `InspectionLogger` class
+
+**Chosen:** A thin `contextmanager` function in `fl_shared/inspection_log.py`:
+
+```python
+from contextlib import contextmanager
+from collections.abc import Generator
+import structlog
+
+@contextmanager
+def inspection_scope(inspection_id: str) -> Generator[None, None, None]:
+    with structlog.contextvars.bound_contextvars(inspection_id=inspection_id):
+        yield
+```
+
+Usage:
+```python
+from fl_shared.inspection_log import inspection_scope
+
+async def my_activity(inspection_id: str) -> None:
+    with inspection_scope(inspection_id):
+        log.info("Work starting")       # inspection_id automatic
+        await _helper()                 # helper's logs get it too
+```
+
+**Rejected alternative — `InspectionLogger` class:**
+A class wrapping structlog's logger API would require every function that logs to receive the logger instance as a parameter, or be constructed at call time with an `inspection_id`. This breaks the standard module-level `log = structlog.get_logger(__name__)` idiom, makes function signatures noisier, and collapses back to using `bound_contextvars` internally anyway. The context manager is the right Python primitive for "ambient data scoped to an execution block."
+
+**Rejected alternative — per-call `inspection_id=` kwargs (current approach):**
+Verbose, error-prone (easy to forget one call), and doesn't propagate to helper functions.
+
+### D2: Move `log_config.py` to `fl_shared`
+
+`fl_shared` is the shared library already imported by `engineering_agent`, `finalizer_agent`, and `fl_mcp_servers`. Moving `log_config.py` there gives all packages access to `configure_logging()` without duplication.
+
+The original `fl_control_plane/log_config.py` is deleted; all imports update to `from fl_shared.log_config import configure_logging`.
+
+### D3: stdlib files get a full structlog conversion, not a bridge
+
+For the five files using `logging.getLogger`, the fix is to replace `logger = logging.getLogger(__name__)` with `log = structlog.get_logger(__name__)` and update call sites.
+
+**Rejected alternative — stdlib-to-structlog bridge:** `log_config.py` already routes stdlib loggers through structlog via `ProcessorFormatter`. A bridge would work for the infrastructure (uvicorn, sqlalchemy) that we don't own. For application code we own, a direct conversion is cleaner and ensures `merge_contextvars` picks up the bound context.
+
+### D4: `inspection_scope` wraps the entire activity body, not individual sections
+
+The context manager goes at the outermost level of each Temporal activity function or FastAPI route handler — wrapping all the work, not just specific log calls. This ensures every helper called from that entry point inherits the context automatically.
+
+```python
+# Correct — wraps everything
+async def extract_data_activity(inspection_id: str) -> None:
+    with inspection_scope(inspection_id):
+        result = await _do_work(inspection_id)  # all logs inside inherit context
+        log.info("Done")
+
+# Wrong — only covers that one section
+async def extract_data_activity(inspection_id: str) -> None:
+    log.info("Starting", inspection_id=inspection_id)  # old pattern
+    with inspection_scope(inspection_id):
+        log.info("Mid-point")
+    log.info("Done", inspection_id=inspection_id)      # must repeat
+```
+
+## Risks / Trade-offs
+
+**[Risk] Temporal activity thread reuse bleeds context between runs**
+→ Mitigation: `bound_contextvars` (context manager form) guarantees cleanup via `__exit__` even if an exception is raised, restoring the previous context. Never use `bind_contextvars` (non-context-manager form) in activities.
+
+**[Risk] Missing entry points — some inspection-scoped paths not covered**
+→ Mitigation: After migration, run an integration test inspection and verify in CLS that all expected log lines carry `inspection_id`. The acceptance criterion in the ticket drives this check.
+
+**[Risk] `fl_shared` version mismatch if packages pin different versions**
+→ Mitigation: All packages in this repo are installed from the local source tree, not independently versioned wheels. This is not a concern for the current monorepo setup.
+
+**[Trade-off] `inspection_scope` is one more import for contributors**
+→ This is intentional. The named import makes the pattern discoverable and searchable, vs. every developer needing to know the structlog API.
+
+## Migration Plan
+
+1. Add `fl_shared/inspection_log.py` and `fl_shared/log_config.py` (moved from `fl_control_plane`)
+2. Update `fl_control_plane` import of `configure_logging` to `fl_shared.log_config`
+3. Delete `fl_control_plane/log_config.py`
+4. Convert stdlib files to structlog one file at a time (low risk — isolated changes)
+5. Add `inspection_scope` at entry points in Temporal activities and route handlers
+6. Remove now-redundant `inspection_id=` per-call kwargs
+7. Update `engineering_agent`, `finalizer_agent`, `fl_mcp_servers` startup imports
+
+No database changes, no API changes, no deployment steps required beyond a normal image rebuild.
+
+**Rollback:** Any step is independently revertable. Logging changes have no impact on data or API contracts.
+

+- Does `finalizer_agent` have an inspection-scoped entry point that should receive `inspection_scope`? (Needs review during implementation.)

+### Requirement: inspection_scope context manager in fl_shared
+`fl_shared` SHALL provide an `inspection_scope(inspection_id: str)` context manager that binds `inspection_id` to the structlog context variable store for the duration of the `with` block. +- **WHEN** code calls `log.info("message")` inside a `with inspection_scope(inspection_id):` block
+- **THEN** the emitted log record SHALL contain `"inspection_id": "<inspection_id>"` as a structured field

+- **WHEN** a helper function called from within a `with inspection_scope(inspection_id):` block calls `log.info("message")` without passing `inspection_id` explicitly
+- **THEN** the emitted log record SHALL contain `"inspection_id": "<inspection_id>"` as a structured field

+- **WHEN** an inner `with inspection_scope(inner_id):` block exits inside an outer `with inspection_scope(outer_id):` block
+- **THEN** log calls after the inner block exits SHALL carry `outer_id`, not `inner_id`
