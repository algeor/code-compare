+### 3.5 Network Topology
+
+FL's network placement affects which external systems it can reach, and how external callers (CI pipelines, BTP apps) can reach FL. This is a critical infrastructure decision because FL must bridge two worlds: SAP-internal CI systems and internet-facing CI systems.
+
+#### FL Runtime: Gardener-Managed Kyma on Monsoon3
+
+**DECIDED:** FL runs on a gardener-managed Kyma cluster in the **monsoon3 domain** (open-source Kyma). This cluster has native connectivity to SAP-internal systems (JaaS, `github.wdf.sap.corp`, internal Vault), which is the primary reason for this choice over a public hyperscaler Kyma cluster.
+
+> **Note:** SCI Kyma on public hyperscalers (AWS/Azure/GCP) does **not** provide SAP-internal network access natively. This assumption was validated and found to be incorrect — Cloud Connector or equivalent is required on those options.
+
+#### Internet-Facing Callers Reaching FL

+FL's Ingestion API must be reachable by callers that run outside the SAP network. Two cases are relevant:

+### 5.5 Known Issue Detection (Handler-Managed Pattern)
+
+At scale, the same root cause can trigger FL analysis repeatedly across many pipeline runs — for example, a flaky infrastructure dependency or a known broken dependency version. Without deduplication, FL schedules a full agent analysis for each occurrence, consuming time and AI tokens to reach the same conclusion every time.
+
+**Design principle:** Known issue detection is **delegated to the handler**, not centralized in the FL control plane. The control plane's role is to orchestrate and execute; business logic — including "have I seen this before?" — belongs in the handler. This keeps the control plane free from domain-specific knowledge and allows different handlers to apply different matching strategies.
+
+#### How It Works
+
+A handler that implements known issue detection maintains its own store (e.g., a database, a file in a well-known location, or an external service) of previously identified root causes. When the handler's k8s Job starts, it:
+
+1. Queries its known issue store using a fingerprint derived from the pipeline failure context (e.g., failed stage name, log patterns, error signatures)
+2. If a high-confidence match is found, the handler returns the stored finding immediately — without invoking the coding agent
+3. If no match is found, the handler proceeds with full analysis and optionally writes the new finding back to the store
+
+This pattern reduces MTTR for recurring failures from minutes (full agent execution) to seconds (store lookup), without requiring any changes to the FL control plane.
+
+#### Contributor Components in the Kyma Cluster
+
+A handler that maintains a known issue store needs somewhere to run long-lived components (e.g., a small API or database). Contributors can deploy such components into the Kyma cluster alongside FL, for example by providing a Helm chart referenced from the contributor registry. This is the same extensibility path available to contributors who need CustomRuntime handler containers. FL does not prescribe the technology; it is the contributor's responsibility to operate and maintain these components.
+
+#### Known Issues via MCP
+
+The FL MCP server (§10.5) exposes a `get_known_issues(query)` tool. Individual handlers that maintain a known issue store can back this tool, enabling developers and coding agents to query known failure patterns directly — even before FL has completed analysis of the current run. This is useful as a fast-path for developers: if the issue is already known, the MCP tool returns the root cause and linked Jira ticket in seconds.
+
+**OPEN:** The contract between a handler's known issue store and the MCP `get_known_issues` tool is not yet defined. This will be addressed when the first contributor implements this pattern.
