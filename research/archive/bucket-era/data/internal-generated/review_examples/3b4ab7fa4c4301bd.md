+# Handler Match Context to MCP Jobs
+
+## Review Scope
+
+Reviewed branch: `pass-failed-stages`
+
+Reviewed commit: `a24219a`

+Compared against: `origin/main` at `1c8eb26`

+
+Merge note: `origin/PIPELINE3-1440` was later merged into this branch. The match-context MCP changes were ported into the `PIPELINE3-1440` unified `_PipelineDataReader` MCP implementation, while preserving the `MCP_MATCH_SCOPE`, `MCP_MATCHED_STAGES`, and `get_failure_focus()` behavior described below.
+
+## Objective
+
+Forward handler match context from the control plane into MCP jobs in a form that an LLM can use safely.
+
+Before this branch, the control plane could identify which failed stage rows matched a stage-scoped handler, but that context stayed mostly internal to orchestration and persistence. A handler subprocess could receive the inspection ID and use MCP tools, but it did not get a clear, handler-specific stage focus.
+
+The branch adds two pieces of context for each handler job:
+
+- `MCP_MATCH_SCOPE`: whether the handler is `pipeline` scoped or `stage` scoped.
+- `MCP_MATCHED_STAGES`: JSON array of failed-stage references with DB ID and CI display name.
+
+It also adds an MCP tool, `get_failure_focus()`, that converts this context into actionable stage and evidence references. Agents should use the returned `StageSummary.dir` value when calling `get_stage_log()` or `get_stage_steps()`, and returned normalized `log_ref` values when calling `get_log_by_ref()`.
+
+## Design Rationale
+
+The important distinction is that `failed_stages.id` is not an HDLF stage directory.
+
+The DB ID is useful for audit and persistence, but MCP stage tools operate on stage directories. If an LLM only sees a DB ID, it can easily try to pass that value into `get_stage_log()` and get a lookup failure.
+
+The branch keeps DB IDs for persistence, but it gives MCP a higher-level contract:
+
+```json
+{
+  "match_scope": "stage",
+  "matched_stages": [
+    {"id": "failed-stage-db-id", "name": "Build"}
+  ]
+}
+```
+
+The MCP server then resolves those stage names against captured stage summaries and returns entries that include the actual `dir` field.
+

+### New MCP Tool: `get_failure_focus()`
+
+File: `fl_mcp_servers/generic/pipeline_data_mcp.py`
+
+New tool:
+
+```python
+async def get_failure_focus(ctx) -> FailureFocus
+```
+
+Behavior:
+
+- Reads all captured stages with `state.reader.list_stages(state.inspection_id)`.
+- If `match_scope == "stage"`:
+  - Builds matched display-name set from `matched_stages[*].name`.
+  - Builds sanitized HDLF-safe dir candidates with `safe_name(name)`.
+  - Returns stages whose `StageSummary.name` matches the display name or whose `StageSummary.dir` matches the sanitized name.
+  - Raises a `ToolError` with guidance to call `get_stage_list()` if no match resolves.
+- If `match_scope == "pipeline"`:
+  - Returns non-success stages when result metadata exists.
+  - Falls back to all stages otherwise.
+
+The result is intentionally resolved focus, not raw match context. This gives agents the `dir` value they need for existing stage tools and normalized log refs they can pass directly to log tools.
+
+Expected LLM flow:
+
+```python
+focus = get_failure_focus()
+log = get_log_by_ref(focus.recommended_read_order[0])
+steps = get_stage_steps(focus.stages[0].stage.dir)
+```

+# Provider Stage ID Hardening Plan
+
+## Goal
+
+Harden handler match context by carrying the provider-native stage identifier from extraction through orchestration, job dispatch, MCP settings, and MCP stage resolution.
+
+Current match context is compatible with the merged `PIPELINE3-1440` unified HDLF schema, but it resolves relevant stages primarily by display name. That is good enough for normal cases, but it is weaker than the new schema allows.
+
+The hardened contract should prefer provider-native stage IDs when available:
+
+```json
+{
+  "id": "failed-stage-db-id",
+  "name": "Build",
+  "provider_stage_id": "stage-1"
+}
+```
+
+Then MCP can resolve relevant stages in this order:
+
+1. `StageSummary.dir == provider_stage_id`
+2. `StageSummary.name == name`
+3. `StageSummary.dir == safe_name(name)`
+
+## Why This Matters
+
+The merged `PIPELINE3-1440` MCP reader supports two layouts:
+
+- Unified HDLF schema: `stages.json`, `steps/<stage_id>.json`, `logs/<stage_id>.log`
+- Legacy Jenkins schema: `stages/<safe_stage_name>/...`
+
+For unified inspections, `_PipelineDataReader.list_stages()` converts each unified `Stage` into a `StageSummary` like this:
+
+```python
+Stage.display_name -> StageSummary.name
+Stage.id           -> StageSummary.dir
+```
+
+The current implementation passes the DB failed-stage ID plus display name. That aligns with the schema because failed-stage rows are currently persisted from provider display names. However, it can become ambiguous when multiple stages/jobs share a name or when a provider changes display-name formatting.
+
+Adding `provider_stage_id` lets MCP resolve the exact stage/job/phase record in the unified schema before falling back to name-based matching.
+
+## Current Cost Estimate
+
+This is a medium-sized hardening change.
+
+- Code files: about 8-12 files
+- Tests: about 5-8 focused tests
+- DB impact: one nullable column plus migration/schema updates
+- Runtime risk: moderate, because the failed-stage persistence contract changes
+- Backward compatibility: manageable if the new field is nullable and all matching keeps name fallbacks
+
+This should be safe to do in the current branch if we keep the change narrow and do not make `provider_stage_id` required.
+
+## Data Model Plan
+

+

+
+Add nullable provider stage ID to `FailedStage`:
+
+```python

+```
+
+Use `String(255)` rather than `String(36)` because provider IDs are not guaranteed to be UUIDs. Azure DevOps timeline record IDs and Jenkins node IDs are provider-native strings.
+
+### Update SQL Schema
+
+File: `db/schema.sql`
+
+Add the column to `failed_stages`:
+
+```sql

+```
+
+Optional index:
+
+```sql

+```
+
+Recommendation: add the index only if we expect DB-side lookups by provider ID. The current runtime uses in-memory orchestration lookup, so this index is not required for the hardening itself.
+

+## Failed-Stage Persistence Plan
+
+### Replace Tuple Contract With a Typed Model
+
+File: `fl_control_plane/metadata_extractor/db_writer.py`
+
+Current contract:
+
+```python
+failed_stages: list[tuple[str, str | None]]
+```
+
+Recommended contract:
+
+```python
+class FailedStageWrite(BaseModel):
+    stage_name: str
+    error_message: str | None = None
+    provider_stage_id: str | None = None
+```
+
+Then:
+
+```python
+async def persist_failed_stages(
+    inspection_id: str,
+    failed_stages: list[FailedStageWrite],
+    db: AsyncSession,
+) -> None:
+    ...
+```
+
+Why not a 3-tuple:
+
+- Tuple position gets unclear quickly.
+- Call sites span ADO, Jenkins, and legacy persistence helpers.
+- A small named model makes test failures and future provider additions easier to read.
+
+Compatibility option:
+
+If minimizing churn is more important, accept both forms temporarily:
+
+```python
+FailedStageInput = FailedStageWrite | tuple[str, str | None]
+```
+
+Recommendation: use only the typed model in this branch. The call surface is small enough.
+

+## Context
+
+The control plane already computes stage-scoped handler matches in the Handler Orchestrator and persists handler-to-failed-stage links for audit. The Execution Engine also forwards basic match context to handler jobs through `MCP_MATCH_SCOPE` and `MCP_MATCHED_STAGES`.
+
+The weak point is the data shape. A `failed_stages.id` row is useful for database correlation, but it is not a valid MCP input for `get_stage_log()` or `get_stage_steps()`. Display names are also lossy: Jenkins stage directories use `safe_name()` plus collision suffixes, and unified CI readers use provider stage IDs as `StageSummary.dir`. The MCP boundary needs to expose actionable identifiers, not internal audit identifiers.
+
+## Goals / Non-Goals
+
+**Goals:**
+
+- Preserve a stable, actionable stage key when failed stages are persisted.
+- Propagate that key through handler matching, job submission, and MCP settings.
+- Give handlers one MCP entry point that returns the failure focus they should inspect first.
+- Keep existing stage/log tools compatible by returning values they already accept.
+- Make ambiguity explicit instead of silently returning the wrong stage.
+
+**Non-Goals:**
+
+- Replace the existing `get_stage_list`, `get_stage_log`, `get_stage_steps`, or normalized log tools.
+- Make the Execution Engine read HDLF while building Kubernetes jobs.
+- Change handler applicability semantics or version selection.
+- Require all historical `failed_stages` rows to be backfilled before deployment.
+
+## Decisions
+
+### Persist an actionable failed-stage key
+
+Add a nullable column to `failed_stages` named `stage_key`. The value is the provider-neutral key that MCP readers can resolve to an actionable `StageSummary.dir`.
+
+- Jenkins Blue Ocean: use the generated stage directory from capture planning, for example `Build` or `Build_42`.
+- Jenkins WFAPI fallback: use the generated safe stage directory when available.
+- Azure DevOps/unified inspections: use the timeline record ID that becomes `StageSummary.dir`.
+
+Alternative considered: resolve the directory later inside the MCP from display names. That keeps the DB unchanged, but duplicate names and sanitized names remain ambiguous.
+
+### Make post-extraction DB persistence authoritative
+
+The workflow runs `persist_inspection_db_activity` after data extraction. That activity currently deletes and reinserts failed-stage rows from HDLF metadata. It must be updated with this change, otherwise any `stage_key` written earlier by provider-specific extractor code can be erased.
+
+The preferred implementation is to make this post-extraction activity the canonical writer for `failed_stages`. Provider-specific extraction should write enough raw or normalized HDLF data for the activity to derive `stage_key`, rather than relying on earlier DB writes that are later overwritten.
+
+Alternative considered: keep provider-specific DB writes and teach the later activity to merge with existing rows. That creates ordering and idempotency risks around delete-before-insert and is harder to reason about during retries.
+
+### Expand `MatchedStageRef`, keep env vars as transport
+
+Extend the shared match-context model to carry `stage_key` and `error_message` in addition to the existing failed-stage DB ID and display name. The Execution Engine continues to serialize this model into `MCP_MATCHED_STAGES` because that is already the isolated job-to-MCP boundary.
+
+Alternative considered: inject a prompt snippet into `TASK_TEXT`. That is less reliable because agents would need to copy strings into tools instead of receiving typed MCP output.
+
+### Introduce a first-class failure focus MCP result
+
+Add `get_failure_focus()` as the preferred first call for fault handlers. Implement it by reusing one internal focus resolver, not by duplicating evidence selection logic. It should return a structured model with:
+
+- `match_scope`
+- resolved focused stages, including `StageSummary.dir`
+- matched failed-stage metadata, including DB row ID and error message when present
+- readable log references and recommended read order when normalized evidence exists
+- resolution method, such as `stage_key`, `display_name`, `safe_name`, or `pipeline_fallback`
+
+Alternative considered: expose a lightweight stage-list-only helper. That improves the immediate issue but does not expose evidence read order or explain why a stage was selected.
+
+### Resolution order is deterministic
+
+For stage-scoped context, the MCP resolver uses this order:
+
+1. Match persisted `stage_key` to `StageSummary.dir`.
+2. Match exact failed-stage display name to `StageSummary.name`.
+3. Match `safe_name(display_name)` to `StageSummary.dir`.
+4. If no match or more than one plausible match remains, return a `ToolError` with guidance to call `get_stage_list()`.
+
+For pipeline-scoped context, the focus tool returns failed or suspicious stages from the failure evidence index when available, then falls back to non-success `StageSummary` rows, then all captured stages.
+
+## Risks / Trade-offs
+
+- **Historical rows lack `stage_key`** -> Keep fallback resolution by display name and safe name.
+- **Duplicate display names remain ambiguous without `stage_key`** -> Return a clear MCP error instead of picking one.
+- **Two data layouts exist during migration** -> Keep the new column nullable and support old `MCP_MATCHED_STAGES` payloads without `stage_key`.
+- **Post-extraction persistence can erase `stage_key`** -> Update `persist_inspection_db_activity` as part of the core implementation and add a regression test for this path.
+- **Focus tool overlaps with evidence tools** -> Use one pure resolver helper and join existing evidence/brief data only when available.
+
+## Migration Plan
+
+1. Add a nullable `failed_stages.stage_key` column through Alembic and update `db/schema.sql` plus ORM models.
+2. Update failed-stage persistence to accept a typed model while still tolerating existing tuple callers during the migration.
+3. Update `persist_inspection_db_activity` to derive and persist `stage_key` from HDLF for Jenkins and unified CI data.
+4. Update or remove provider-specific failed-stage DB writes so they cannot be overwritten with weaker `(name, error)` rows later.
+5. Expand match context serialization/deserialization and keep absent fields backward compatible.
+6. Add one pure MCP focus resolver and expose `get_failure_focus()`.
+7. Add tests for migration compatibility, exact key resolution, ambiguous fallback, pipeline fallback, and post-extraction overwrite regression.
+
+Rollback is safe because the new DB column is nullable and old MCP payloads remain parseable. If the focus tool is disabled, handlers can still use existing `get_stage_list()` and stage log tools.
+
+## Open Questions
+
+- None. `get_failure_focus()` is the single public focus tool.
