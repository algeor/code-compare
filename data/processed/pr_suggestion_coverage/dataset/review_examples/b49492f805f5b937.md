+## PHASE 4e — Adversarial Verification & Community Research
+
+After deduplication, each non-PRAISE finding is too expensive to trust at face value. Reviewers hallucinate issues, misread context, and project assumptions onto unfamiliar code. This phase spawns two waves of agents per finding to stress-test it before it reaches the final report.
+
+**Critical mindset**: Do NOT start with the assumption that the finding is correct. Start from the assumption that you might be wrong. Check the dependency docs. Check the library source. Check the actual runtime behavior. A finding that survives adversarial verification is worth 10 that were rubber-stamped.
+
+### 4e-i. Adversarial Testing Agents (one per finding, parallel)
+
+For each BLOCKER or WARNING finding, spawn an agent whose sole job is to **try to disprove it**:
+
+```
+You are an adversarial tester. Your job is to DISPROVE the following code review finding.
+Do NOT start with the assumption the finding is correct.
+
+## The Finding
+{finding_title}: {finding_detail}
+File: {file}:{line}
+
+## Your Approach
+
+1. **Check dependencies first** — Read the actual library/framework docs or source.
+   Does the dependency behave the way the reviewer assumed? Many findings are based
+   on incorrect assumptions about how a library works.
+2. **Trace the actual execution path** — Don't theorize. Read the code. Follow the
+   call chain. Does the problematic scenario the reviewer describes actually occur
+   given the real control flow?
+3. **Check for existing guards** — Is there upstream validation, a middleware,
+   a decorator, or a Pydantic model that already prevents the scenario?
+4. **Test from multiple angles**:
+   - What does the test suite already cover for this code path?
+   - Does the CI pipeline catch this class of issue?
+   - Is there a runtime safety net (K8s restart policy, retry logic, circuit breaker)?
+5. **Check version-specific behavior** — Is the reviewer's concern valid for the
+   actual pinned version of the dependency, or only for an older/newer version?
+
+## Output Format
+
+- **Verdict**: CONFIRMED | REFUTED | DOWNGRADED | UNCERTAIN
+- **Evidence**: Specific file/line/doc references that support your verdict
+- **Reasoning**: Why you believe the finding is/isn't valid
+- **Dependency Check**: What you verified about library behavior (with source)
+
+If REFUTED: The finding is wrong — explain why with evidence.
+If DOWNGRADED: The finding has merit but severity is too high — suggest correct severity.
+If CONFIRMED: You tried to disprove it and couldn't — it's a real issue.
+If UNCERTAIN: You couldn't conclusively prove or disprove — flag for human judgment.
+```
+
+### 4e-ii. Community Research Agents (one per CONFIRMED finding, parallel)
+
+For each finding that survives adversarial testing (verdict = CONFIRMED or DOWNGRADED), spawn a research agent to find the **best informed fix according to community standards**:
+
+```
+You are a community standards researcher. A code review finding has been confirmed as valid.
+Your job is to find the BEST way to fix it — not the fastest, not the most clever, but the
+most aligned with how the broader community solves this exact problem.
+
+## The Confirmed Finding
+{finding_title}: {finding_detail}
+File: {file}:{line}
+Adversarial verdict: {verdict} — {adversarial_reasoning}
+
+## Your Research Approach
+
+1. **Identify the ecosystem** — What framework/library is involved? (FastAPI, Pydantic,
+   kopf, kubernetes-client, SQLAlchemy, etc.)
+2. **Check official docs** — Does the framework have a recommended pattern for this?
+   Use WebFetch on official documentation URLs.
+3. **Check GitHub issues/discussions** — Has the community encountered and solved this
+   exact problem? Search for similar issues in the framework's repository.
+4. **Check established patterns** — What do popular open-source projects using the same
+   stack do in this situation? (e.g., how do other kopf operators handle this pattern?)
+5. **Evaluate tradeoffs** — If multiple solutions exist, which fits THIS project's
+   constraints (CLAUDE.md standards, existing patterns, deployment model)?
+
+## Output Format
+
+- **Recommended Fix**: The community-standard solution with code example
+- **Source**: Where this pattern comes from (doc URL, GitHub issue, well-known project)
+- **Why This Over Alternatives**: What other approaches exist and why this one is better
+  for this specific codebase
+- **Migration Risk**: How invasive is this fix? Does it touch contracts/APIs?
+- **Confidence**: HIGH (official docs recommend this) | MEDIUM (common community pattern)
+  | LOW (best guess from limited sources)
+```
+
+### 4e-iii. Reconciliation
+
+After both waves complete:
+- **REFUTED findings** are removed from the report entirely (with a note in Pre-Review Notes that N findings were disproven during verification)
+- **DOWNGRADED findings** have their severity adjusted per the adversarial agent's recommendation
+- **CONFIRMED findings** are enriched with the community research agent's recommended fix (replaces the original reviewer's suggested fix if the research agent's is more informed)
+- **UNCERTAIN findings** are kept at original severity but marked with ⚠️ "Unverified — reviewer judgment, not independently confirmed"
+
+This phase may reduce the total finding count significantly. That is the point — fewer, higher-confidence findings are more actionable than a wall of unverified opinions.
