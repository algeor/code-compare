+# Python Code Style Guide
+
+## Imports
+
+- Order: standard library → third-party → local, alphabetical within each group
+- Multi-line imports use parentheses, never backslashes
+- Add `# type: ignore` for untyped third-party packages
+- Alias imports when the original name is ambiguous or conflicts
+
+## Type Annotations
+
+- Every function parameter and return type must be annotated
+- Prefer `str | None` over `Optional[str]` and `list[str]` over `List[str]`
+- Use `typing.Literal` for constrained string or enum-like values
+
+## Naming
+
+- `snake_case` for functions, variables, and modules
+- `UPPER_SNAKE_CASE` for module-level constants; `_UPPER_SNAKE_CASE` if private
+- `PascalCase` for classes including TypedDicts
+- `_leading_underscore` prefix for private functions
+- Variable names must be self-describing in isolation — never abbreviate. Write `node_id`, `step_start`, `raw_step`, not `nid`, `sstart`, `s_raw`. Suffixes like `_id`, `_start`, `_end`, `_raw` only carry meaning with their full domain prefix.
+
+## Classes and Data Structures
+
+- Use **Pydantic `BaseModel`** for all data structures — internal and especially those from external sources
+- Pydantic validates schema on construction, catching hallucinated or unexpected fields from LLMs and external APIs early
+- Reserve plain classes for entities with behavior (e.g., clients, services) that do not need validation
+- Prefer composition over inheritance
+- Keep inheritance hierarchies shallow and intentional
+
+## Pydantic API Boundary Pattern
+- When consuming external API responses (Jenkins, Azure DevOps, GitHub, Jira, etc.), define **two** model layers:
+  1. **Raw models** (`Raw*`): Mirror the exact API response shape. Use `Field(alias="...")` for JSON keys that aren't valid Python identifiers (e.g. `_class`). Set `model_config = {"populate_by_name": True}` when aliases are used. Validate at the boundary with `RawModel.model_validate(api_json)`.
+  2. **Output models**: Clean, snake_case, project-oriented representations returned to callers. These are what MCP tools and internal code work with.
+- Raw models include `.to_*()` converter methods that produce the corresponding output model (e.g. `RawBuildResponse.to_build_info() -> BuildInfo`).
+- Never pass raw `Dict[str, Any]` through internal code for structured data — always parse into a Pydantic model at the boundary.
+- **Public method return types must be named Pydantic output models, not `dict[str, Any]`.** A `dict[str, Any]` return type is only acceptable at true serialization boundaries where the caller immediately converts to untyped output (e.g., an MCP tool that calls `.model_dump()` before returning to the JSON-RPC layer).
+- Place models in the same module as the API client that uses them, or in a dedicated `*_models.py` file when shared across modules.
+
+
+## Pydantic Model Docstrings
+
+Every non-trivial Pydantic model needs a class docstring. The purpose is to close the gap between what the type annotation expresses and what the actual contract requires. Ask three questions for every model and every field:
+
+**1. What can the type annotation not tell you?** (domain semantics)
+- What are the actual values this field can take? (informal enums like `"SUCCESS" | "FAILURE" | "UNSTABLE" | "ABORTED"`)
+- What does `None` mean here — missing, not applicable, indeterminate, or not yet computed?
+- Does the field name imply something different from what it contains? (e.g. `pipeline` is a branch name not a job name; `firstParent` of a STAGE node is a sequential predecessor not a tree parent)
+
+**2. What does the producer guarantee that the type system cannot enforce?** (producer invariants)
+- Are fields mutually exclusive? (if A is set, B is always `None` — and vice versa)
+- Is a field only populated under certain conditions? (only when `ran=True`, only in search mode)
+- Are values in one field constrained or derived from another?
+
+**3. What does a consumer need to use this correctly?** (consumer guidance)
+- Which field to check first when multiple fields could apply?
+- Can field values be reused as inputs to other calls? (e.g. line numbers from `matched_lines` → `line_from`/`line_to`)
+- Which fields are unreliable or approximate, and what is the workaround? (e.g. `commit_url` is often `None`; `failure_message` is truncated — use `query_junit` for full text)
+
+Structure every docstring in four parts:
+1. **Provenance** — exact endpoint URL (raw models) or client method (output models). For models assembled from multiple sources, list each source and what it contributes (primary/secondary) — the source determines which fields are reliable and what the fallback chain is.
+2. **Architectural context** — only when the source choice is non-obvious. Omit otherwise.
+3. **Example** — real data from a test notebook (`model_dump()` or raw `.json()` output), labelled with build/PR identifiers so the reader can trace it. Use two contrasting examples when the model has conditional field population — a single example hides invariants.
+4. **Attributes** — one entry per field where any of the three questions above has a non-trivial answer. Skip self-explanatory fields. Do not paraphrase the type annotation.
+
+Additional rules:
+- Remove inline field comments (`# branch name`) once the Attributes section covers them.
+- For `dict[str, Any]` fields with format-dependent schemas, inline all per-format schemas in the Attributes entry — do not force the reader to find the parsing function.
+- Use `⚠️` to mark fields where misreading the contract silently produces wrong results (not just inconvenient ones).
+- Use real data verified against an actual API call for examples — test notebooks, integration test fixtures, recorded responses, or saved `model_dump()` output. Never invent data.
+
+## Functions
+
+- Short, focused utility functions are preferred
+- Long orchestration functions are acceptable if they delegate to named helpers
+- Private helpers live in the same module with a `_` prefix
+- No speculative abstraction — functions do exactly what is needed, nothing more
+
+## Error Handling
+
+- Build a custom exception hierarchy: `BaseError → DomainError → SpecificError`
+- Use factory functions to select the right exception subclass when the mapping is non-trivial
+- Catch specific exception types only — never bare `except Exception`
+- Chain exceptions with `raise X from e`
+- Validate preconditions at function entry with `raise ValueError`
+
+## Comments and Docstrings
+
+- Use `TODO:` / `FIXME:` for acknowledged tech debt
+- Docstrings use **Google style** (Args / Returns / Raises sections) with imperative mood ("Build", "Get", "Parse")
+- Module-level docstrings: one line describing the module's responsibility
+
+### The one rule for inline comments
+
+**Write a comment only when a future reader with no context would look at the line and think "that's weird, I should simplify this."**
+
+If they'd just nod and move on, the code is self-explanatory — no comment needed.
+
+Comments belong in exactly five situations:
+
+1. **A known failure mode** — something that looks safe but breaks in a specific case  
+   *"must NOT be masked because blind str.replace() corrupts diffs … causing UnidiffParseError"*
+
+2. **A platform or language subtlety the reader might not know**  
+   *"POSIX allows empty environment variables. However, in our well-defined set, empty is always invalid."*
+
+3. **A security or correctness invariant that looks like a bug**  
+   *"raise … from None — suppresses chain intentionally: the original exception may contain the secret value being masked"*
+
+4. **A non-obvious behavioral dependency**  
+   *"start_new_session=True — ensures CTRL-C reaches Python, not the child process"*
+
+5. **Non-obvious behavior of an external dependency**  
+   Document it at the point of handling. The threshold is: *would a reader who knows the language but has never used this specific API understand why without looking it up?* If not, write it down.  
+   Use a docstring when the behavior is the central concern of the function; use an inline comment when it explains a single line.  
+   Name the dependency, describe the behavior, state the consequence of ignoring it, and link to a ticket or spec when one exists.
+
+   Examples of what to document:
+   - Protocol quirks: *"Gerrit prepends `)]}'` to every JSON response to prevent XSSI — strip before parsing"*
+   - Synthetic data: *"Gerrit includes `/COMMIT_MSG` as a virtual file in diff listings — filter paths starting with `/`"*
+   - Required query parameters: *"Must request `ALL_REVISIONS` option or the `revisions` map is absent from the response"*
+   - Lifecycle states: *"`dep.details` is `None` while the deployment is still starting"*
+   - URL construction: *"Base URL may include `/v2`, but quota endpoints prepend their own — strip it or requests double-version"*
+   - Known bugs: *"FIXME: `|` in type annotations crashes the Thinktank parser — see JIRA-1234"*
+   - Encoding: *"Credentials may appear URL-encoded inside git remote URLs embedded in subprocess args — mask both forms"*
+
+In every case the comment answers: **"Why didn't you do the obvious thing?"** — and names the exact consequence of doing it the naive way.
+
+## Configuration and Environment
+
+- Use **Pydantic Settings** (`pydantic-settings`, `BaseSettings`) for all configuration — never `os.environ` or `os.getenv` directly in application code
+- **Prefer a single project-wide `Settings` class** (e.g. `config.py`) that covers all environment variables; only split into a per-module `Settings` when a subsystem is genuinely isolated and has no overlap with the global config
+- Validation happens automatically at instantiation — required fields with no default raise a `ValidationError` on startup, not at point of use
+- Secret fields use `SecretStr`; call `.get_secret_value()` only at the point of actual use, never earlier
+
+## Tests
+
+- One-line docstring per test stating the invariant being tested
+- Test function names describe the behavior: `test_<behavior>()`
+- Mock at the boundary closest to the code under test
+- Assertions should be direct: equality checks, exception assertions, and state inspection
