+## Summary
+
+Reviewed the execution engine implementation covering RBAC provisioning, job restartability, generalised `_build_job`/`dispatcher.py`, path updates, and conditional finaliser invocation. The implementation is structurally sound and the concurrency model is correct. Three blockers were found: a crash in `_job_status` when Kubernetes returns a job whose `.status` field is `None` (common for freshly-created jobs), an over-privileged RBAC Role that grants every handler pod the ability to read and patch any ConfigMap in the namespace, and a service-account name duplicated between `rbac.py` and `dispatcher.py` as separate string literals that can silently diverge. Six warnings cover bare `except Exception` catches, `Optional[...]` style violations, missing Pydantic model docstrings, and the handler dict remaining untyped. Four informational items round out minor issues.

+### CR-01: `_job_status` crashes with `AttributeError` when `job.status` is `None`
+
+**File:** `fl_control_plane/execution_engine/dispatcher.py:206`
+
+**Issue:** The Kubernetes Python client returns a `V1Job` whose `.status` attribute is `None` until the control plane has processed the newly-created job. Line 206 accesses `job.status.conditions` unconditionally. When `.status` is `None` this raises `AttributeError: 'NoneType' object has no attribute 'conditions'`, propagating unhandled through `_wait_for_job` and crashing `run()` via `executor.map`. The existing test (`test_job_status_still_running`) only covers the `conditions = []` case and does not exercise `status = None`.
+
+Reproduced in isolation:
+```python
+job.status = None
+job.status.conditions or []  # -> AttributeError
+```
+
+**Fix:**
+```python
+def _job_status(job_name: str) -> str | None:
+    """Return terminal status of a k8s Job, or None if still running."""
+    job = client.BatchV1Api().read_namespaced_job(job_name, settings.namespace)
+    if job.status is None:
+        return None
+    for condition in job.status.conditions or []:
+        if condition.status == "True":
+            if condition.type == "Complete":
+                return "succeeded"
+            if condition.type == "Failed":
+                return "failed"
+    return None
+```
+
+Add a corresponding test:
+```python
+def test_job_status_returns_none_when_status_is_none():
+    """_job_status returns None (not AttributeError) when job.status is not yet populated."""
+    job = MagicMock()
+    job.status = None
+    with patch("dispatcher.client.BatchV1Api") as mock_cls:
+        mock_cls.return_value.read_namespaced_job.return_value = job
+        assert dispatcher._job_status("fl-job-abc") is None
+```

+### CR-02: RBAC Role grants handler pods read/patch access to ALL ConfigMaps in the namespace
+
+**File:** `fl_control_plane/execution_engine/rbac.py:48-55`
+
+**Issue:** The Role created by `_ensure_role` grants `get` and `patch` on `configmaps` with no `resourceNames` restriction. Every handler pod running as `fl-execution-agent` can therefore read or patch any ConfigMap in the namespace — including those owned by other services, other pipelines, or Kubernetes system components. In a shared namespace this is a lateral-movement vector: a compromised or misbehaving pod can exfiltrate or corrupt configuration data that belongs to unrelated workloads.
+
+Each agent pod already knows its own ConfigMap name via the `TASK_ID` env var, so it does not need namespace-wide access.
+
+**Fix:** Restrict the role to only ConfigMaps matching the `fl.sap.com/run-id` label, or use `resourceNames` if the names are known at provisioning time. The cleanest approach is a per-execution Role with an exact `resourceNames` entry:
+
+```python
+# in _ensure_role, pass resource_names so each pod can only touch its own CM
+client.V1PolicyRule(
+    api_groups=[""],
+    resources=["configmaps"],
+    resource_names=[f"fl-cm-{short_execution_id}"],  # scoped to this execution
+    verbs=["get", "patch"],
+)
+```
+
+If a single shared role is preferred, scoping by label requires an admission webhook or OPA policy rather than a native RBAC rule. At minimum, document the accepted blast radius and add a comment explaining why namespace-wide access is required.

+### CR-03: Service account name is duplicated as independent string literals in two modules
+
+**File:** `fl_control_plane/execution_engine/rbac.py:17` and `fl_control_plane/execution_engine/dispatcher.py:116`
+
+**Issue:** `rbac.py` defines `_SERVICE_ACCOUNT_NAME = "fl-execution-agent"` and `dispatcher.py` hardcodes `service_account_name="fl-execution-agent"` in `_build_job`. There is no import or shared constant linking them. If one is changed without updating the other, every dispatched job will run under a service account that has no RBAC permissions, causing silent runtime failures (the pods will receive 403s when they attempt to patch their ConfigMaps). The mismatch is invisible at test time because the service account name is never validated against what `ensure_rbac` created.
+
+**Fix:** Export the constant from `rbac.py` and import it in `dispatcher.py`:
+
+```python
+# rbac.py — make it importable (remove leading underscore)
+SERVICE_ACCOUNT_NAME = "fl-execution-agent"
+
+# dispatcher.py
+from rbac import ensure_rbac, SERVICE_ACCOUNT_NAME
+# ...
+service_account_name=SERVICE_ACCOUNT_NAME,
+```

+### WR-04: Handler spec is passed as `dict[str, Any]` throughout — no Pydantic validation at the boundary
+
+**File:** `fl_control_plane/execution_engine/dispatcher.py:33,46,132`, `fl_control_plane/execution_engine/repository.py:14,15,31,33,36`
+
+**Issue:** CLAUDE.md states "Use Pydantic `BaseModel` for all data structures — internal and especially those from external sources." The handler spec (carrying `metadata.name`, `spec.fault_id`, `spec.execution.type`, etc.) is passed as a raw `dict[str, Any]` from the repository through `dispatch_all`, `_dispatch_handler`, `_build_configmap`, and `_task_text`. Structural errors in incoming handler data (missing `spec`, wrong field names) cause silent `None` fallbacks (`handler.get("metadata", {}).get("name", "unknown")`) rather than validation errors at the ingestion boundary.
+
+**Fix:** Define a `HandlerSpec` model (with nested `HandlerExecution`) and parse at the point of ingestion:
+```python
+class HandlerExecution(BaseModel):
+    type: str = "agent_task"
+    task: str = ""
+    image: str | None = None
+    mcp_config_paths: list[str] = []
+    skill_paths: list[str] = []
+
+class HandlerSpec(BaseModel):
+    fault_id: str
+    execution: HandlerExecution
+
+class Handler(BaseModel):
+    metadata: dict[str, str]  # or a dedicated Metadata model
+    spec: HandlerSpec
+```

+### WR-05: `_wait_for_job` has no upper bound — can block the calling thread indefinitely on infrastructure failures
+
+**File:** `fl_control_plane/execution_engine/dispatcher.py:215-221`
+
+**Issue:** `_wait_for_job` loops forever calling `read_namespaced_job`. If the Kubernetes API server becomes unreachable, the `read_namespaced_job` call blocks until a default TCP timeout (which can be minutes), then the loop retries immediately, blocking again. No `_request_timeout` is passed to the API call, and there is no circuit-breaker or wall-clock deadline. Since `run()` uses `executor.map(_wait_for_job, findings)`, a hung poll blocks the thread until the job's `active_deadline_seconds` (up to 3600 s) eventually produces a terminal condition — assuming k8s connectivity resumes.
+
+**Fix:** Pass a request timeout to each API call and optionally add a wall-clock deadline:
+```python
+def _wait_for_job(finding: HandlerFinding) -> HandlerFinding:
+    """Poll until the job reaches a terminal state, then return finding with status set."""
+    while True:
+        status = _job_status(finding.job_name)
+        if status is not None:
+            return finding.model_copy(update={"status": status})
+        time.sleep(settings.job_poll_interval_seconds)
+
+def _job_status(job_name: str) -> str | None:
+    job = client.BatchV1Api().read_namespaced_job(
+        job_name, settings.namespace, _request_timeout=30
+    )
+    ...
+```

+# Execution Engine — Known Gaps
+
+Features identified as missing from the current execution engine implementation.
+Each row links to the relevant architecture section for context.
+
+| Feature | Gap | Architecture Ref |
+|---|---|---|
+| **ConfigMap cleanup on completion** | ConfigMaps are created on dispatch and deleted only on creation failure — never cleaned up after the job finishes normally. The Job already has ttl_seconds_after_finished=3600 so pods and job resources clean themselves up. The ConfigMap lingering is just a tidiness issue — not a correctness one. The natural place to delete the ConfigMap is inside the real finalizer, once it's implemented. Doing it now in the stub means writing cleanup logic twice. | — |
+| **Per-handler secret injection** | Right now there's one global secret (e.g. engineering-agent-creds) that gets injected into every pod — it contains things like API keys for Cline Central and Doit. Every handler job gets the same credentials. <br> The gap refers to a future requirement where different handlers might need different secrets. For example, a SonarQube handler might need a SonarQube token, while a Gerrit handler needs a Gerrit password. The architecture design envisions FL resolving which secrets each handler needs at dispatch time and injecting only the relevant ones into that handler's pod. Handlers can declare `secret_names` in their execution spec and those secrets are referenced in the pod's `envFrom`. However, secrets must be pre-created in the cluster manually — the execution engine does not create or validate them. If a named secret does not exist, the pod fails with `CreateContainerConfigError`. The full design requires FL to dynamically resolve and provision per-handler credentials at dispatch time (e.g. from a secrets store), rather than relying on ops to pre-create them. | §8.4, §8.5 |
+| **Resource limits** | No CPU or memory limits set on the job container | §16.1 |
+| **Job status tracking** | No execution state is persisted to the database — `HandlerFinding` status is tracked in memory only | §14 |
+| **Prometheus metrics** | No `fl_handler_executions_total`, `fl_handler_duration_seconds`, or AI token usage metrics are recorded | §14.1 |

+"""Agent task runner — synchronous; called directly by scripts/run_agent_task.py.
+
+All pipeline3 and scheduling_doit calls are sequenced here in a single function.
+Tests can patch 'app.agent_task_runner.pipeline3' and 'app.agent_task_runner.scheduling_doit'
+via unittest.mock.patch.
+"""
+from __future__ import annotations
+
+import logging
+
+from app.models import AgentTaskRequest, AgentTaskResult, RawTrajectory
+
+log = logging.getLogger(__name__)
+
+from hana_program_synthesis.cline_central_api import pipeline3, scheduling_doit
+
+
+def _adjust_resource_requirements(task: dict) -> None:
+    """Override default HANA-sized Doit resource requirements with FL-appropriate values.
+
+    The SDK defaults (4 CPUs, 16 GiB RAM) target large HANA Core analysis tasks and
+    cause long scheduling queues. FL fault analysis is lightweight and completes fine
+    on smaller allocations, reducing queue wait time significantly.
+    """
+    task["requirement_cpus_n"] = 1
+    task["requirement_mem_gib"] = 4
+    task["requirement_disk_gib"] = 8
+
+
+def _build_result(
+    task_id: str,
+    traj: RawTrajectory,
+    completion_text: str,
+    repo_diff: str | None,
+) -> AgentTaskResult:
+    """Assemble an AgentTaskResult from a completed trajectory.
+
+    Extracts token counts from the cline_state JSON if available. Token extraction
+    failure is non-fatal — the result is returned with tokens_in/tokens_out as None.
+    """
+    result = AgentTaskResult(
+        task_id=task_id,
+        mlflow_run_id=traj.mlflow_run_id,
+        completion_text=completion_text,
+        repo_diff=repo_diff,
+    )
+
+    try:
+        cline_state = traj.parse_cline_state()
+        item = cline_state.current_task_item
+        if item is not None:
+            result.tokens_in = item.tokens_in
+            result.tokens_out = item.tokens_out
+    except Exception:
+        log.warning("Failed to extract token counts for task %s", task_id, exc_info=True)
+
+    return result
+
+
+def run(request: AgentTaskRequest) -> AgentTaskResult:
+    """Execute a single agent task synchronously.
+
+    Must be called from a thread (via run_in_executor) — never from the async event loop.
+
+    SECURITY: Never logs environment_variables values.
+    """
+    log.info("Agent task runner started: task_id=%s repo_url=%s", request.task_id, request.repo_url)

+"""K8s Job entrypoint — reads task config from env vars, runs agent_task_runner directly.
+
+Usage:
+    Set env vars (via ConfigMap + Secret) and run:
+        python scripts/run_agent_task.py
+
+    Result is printed as JSON to stdout. Exit code 0 = success, 1 = error.
+"""
+from __future__ import annotations
+
+import logging
+import sys
+
+from pydantic import ValidationError
+
+from app.client_reporter import report_result
+from app.config import JobSettings
+from app.models import AgentTaskRequest
+
+
+def main() -> None:
+    logging.basicConfig(level=logging.INFO, stream=sys.stderr,
+                        format="%(asctime)s %(levelname)s %(name)s %(message)s")
+
+    log = logging.getLogger(__name__)
+
+    try:
+        settings = JobSettings()
+    except ValidationError as exc:
+        log.error("Error loading environment configuration: %s", exc)
+        sys.exit(1)
+
+    # Deferred import — logging must be configured before agent_task_runner loads,
+    # as it initialises loggers at import time.
+    from app import agent_task_runner
+
+    try:
+        request = AgentTaskRequest(
+            task_id=settings.task_id,
+            task_text=settings.task_text,
+            repo_url=settings.repo_url,
+            repo_commitish=settings.repo_commitish,
+            config_repo_url=settings.config_repo_url,
+            config_repo_commitish=settings.config_repo_commitish,
+            config_mcp_paths=settings.config_mcp_paths,
+            config_skill_paths=settings.config_skill_paths,
+        )
+    except ValidationError as exc:
+        log.error("Error building agent task request: %s", exc)
+        sys.exit(1)
+
+    try:
+        result = agent_task_runner.run(request)
+    except Exception:
+        log.error("Unhandled exception in agent task runner", exc_info=True)
+        sys.exit(1)
+
+    report_result(result)
+
+
+if __name__ == "__main__":
+    main()
