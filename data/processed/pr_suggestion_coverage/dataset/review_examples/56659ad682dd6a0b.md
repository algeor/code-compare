+# Creating Piper CI/CD Secrets in Vault
+
+This document describes how to create the two Vault secrets the Piper CI/CD
+pipeline for `pipeline-fl-handlers-impl` consumes:
+
+| Purpose | Vault path | Secret key |
+| --- | --- | --- |
+| Deploy to the FL control-plane cluster | `pipeline-fl-control-plane/kube-config` | `kubeConfig` |
+| Push the built image to the Keppel registry | `sap-project-pipeline-fl/GROUP-SECRETS/docker-config` | `dockerConfigJSON` |
+
+## Prerequisites
+
+- Vault server and namespace (from `.pipeline/config.yml`):
+  - Server: `https://vault.tools.sap`
+  - Namespace: `ies/hyperspace/pipelines`
+- Write permission on the two paths above.
+- Create a technical user for keppel repository
+
+## How Piper resolves these paths
+
+`.pipeline/config.yml` sets:
+
+```yaml
+general:
+  vaultServerUrl: 'https://vault.tools.sap'
+  vaultNamespace: 'ies/hyperspace/pipelines'
+  vaultBasePath:  'piper/sap-project-pipeline-fl'
+  vaultPath:      'piper/sap-project-pipeline-fl'
+  vaultPipelineName: 'pipeline-fl-handlers-impl'
+```
+
+Piper reads a secret by looking up a **key** (e.g. `kubeConfig`) under a set of
+Vault paths derived from `vaultBasePath` / `vaultPath` and
+`vaultPipelineName`. The two paths below are the ones this pipeline uses; keep
+the path segments and the secret keys **exactly** as written — Piper matches on
+those names.
+
+---
+
+## Secret 1 — Kubernetes kubeconfig (cluster deploy)
+
+- **Path:** `pipeline-fl-control-plane/kube-config`
+- **Key:** `kubeConfig`
+- **Used for:** deploying to the cluster
+  `api.ppln-fl-dev.pipelinefl.shoot.canary.k8s-hana.ondemand.com`.
+
+The value is the **entire kubeconfig YAML**, stored as the string value of the
+`kubeConfig` key.
+
+`kubeconfig.yaml` has this shape (values redacted):
+
+```yaml
+apiVersion: v1
+kind: Config
+current-context: piper-deploy
+contexts:
+  - name: piper-deploy
+    context:
+      cluster: shoot
+      user: piper-deploy
+clusters:
+  - name: shoot
+    cluster:
+      server: https://api.ppln-fl-dev.pipelinefl.shoot.canary.k8s-hana.ondemand.com
+      certificate-authority-data: <BASE64_CA_CERT>
+users:
+  - name: piper-deploy
+    user:
+      token: <SERVICE_ACCOUNT_TOKEN>
+```
+
+### Via the Vault UI
+
+1. Navigate to `piper/sap-project-pipeline-fl/pipeline-fl-control-plane/kube-config`.
+2. Create a secret with key `kubeConfig`.
+3. Paste the full kubeconfig YAML as the value.
+
+### Verify
+
+```sh
+vault kv get \
+  -field=kubeConfig \
+  piper/sap-project-pipeline-fl/pipeline-fl-control-plane/kube-config \
+  | head -5
+```
+
+---
+
+## Secret 2 — Docker registry config (image push)
+
+- **Path:** `sap-project-pipeline-fl/GROUP-SECRETS/docker-config`
+- **Key:** `dockerConfigJSON`
+- **Used for:** pushing the built image to
+  `keppel.eu-de-1.cloud.sap` (target `hana-qa-lenny/pipeline-fl-handlers-impl`,
+  see `imagePushToRegistry` in `.pipeline/config.yml`).
+
+The value is a **Docker config JSON document** (the same shape as
+`~/.docker/config.json`), stored as the string value of the `dockerConfigJSON`
+key:
+
+```json
+{
+  "dockerConfigJSON": {
+    "auths": {
+      "keppel.eu-de-1.cloud.sap": {
+        "auth": "<BASE64_OF_username:password>"
+      }
+    }
+  }
+}
+```
+
+Technical user MUST be created from keppel UI -> https://dashboard.eu-de-1.cloud.sap/monsoon3/hana-qa-infrastructure/identity/app-credentials
+
+The `auth` field is `base64(username + ":" + password)`. For Keppel the
+username is the application-credential id and the password is its secret:
+
+```sh
+# Build the auth value (do this in a shell that does not persist history).
+printf '%s' 'applicationcredential-<ID>:<SECRET>' | base64
+```
+
+### Via the Vault CLI
+
+Store the JSON from a file so it is kept verbatim:
+
+> Note the path passed to Vault is `piper/sap-project-pipeline-fl` (the
+> `vaultBasePath`) followed by the secret path
+> `sap-project-pipeline-fl/GROUP-SECRETS/docker-config`. Confirm against your
+> Vault mount layout — the `GROUP-SECRETS` segment indicates this is a group-
+> level secret shared across the project's pipelines, so it may already exist.
+
+### Verify
+
+```sh
+vault kv get \
+  -field=dockerConfigJSON \
+  piper/sap-project-pipeline-fl/sap-project-pipeline-fl/GROUP-SECRETS/docker-config \
+  | python -m json.tool
+```

+# Release Setup — Promoting Images to JFrog
+
+This document describes how to enable the release promotion step in the Piper
+pipeline so built images are promoted to the JFrog `deploy-releases` registry.
+
+## 1. Enable staging service in the Promote stage
+
+In `.pipeline/config.yml`, change the `Promote` stage's `sapCallStagingService`
+flag from `false` to `true`:
+
+```yaml
+stages:
+  # ...
+  Promote:
+    sapCallStagingService: true
+```
+
+The step configuration it uses is already defined further down in the same
+file, so no other change is needed:
+
+```yaml
+steps:
+  sapCallStagingService:
+    url: 'https://staging.repositories.cloud.sap/stage/api'
+    profile: 'group-sap-pipeline-fl-project-default'
+```
+
+Make this change on a separate branch — never commit or push directly to
+`main` (a push to `main` triggers the productive pipeline). Open a pull request,
+and once merged the pipeline runs the Promote stage.
+
+## 2. Read the Promote step logs
+
+After the Promote stage runs, its GitHub Actions logs print the promoted
+images. The line looks like this:
+
+```
+Promoted Docker images are : '[deploy-releases-****-docker.common.repositories.cloud.sap/pipeline-fl-control-plane-engineering_agent:0.0.1-20260724071739_adc5e7b97a6a52ace84a17ee0b9583b45632b275 deploy-releases-****-docker.common.repositories.cloud.sap/pipeline-fl-control-plane-fl_mcp_servers:0.0.1-20260724071739_adc5e7b97a6a52ace84a17ee0b9583b45632b275 deploy-releases-****-docker.common.repositories.cloud.sap/pipeline-fl-control-plane:0.0.1-20260724071739_adc5e7b97a6a52ace84a17ee0b9583b45632b275]']'
+```
+
+The bracketed list contains one entry per promoted image. Each entry is:
+
+```
+deploy-releases-****-docker.common.repositories.cloud.sap/<image-name>:<version>-<timestamp>_<git-sha>
+```
+
+For the example above, the three promoted images are:
+
+| Image name                                    | Tag                                                             |
+| --------------------------------------------- | --------------------------------------------------------------- |
+| `pipeline-fl-control-plane-engineering_agent` | `0.0.1-20260724071739_adc5e7b97a6a52ace84a17ee0b9583b45632b275` |
+| `pipeline-fl-control-plane-fl_mcp_servers`    | `0.0.1-20260724071739_adc5e7b97a6a52ace84a17ee0b9583b45632b275` |
+| `pipeline-fl-control-plane`                   | `0.0.1-20260724071739_adc5e7b97a6a52ace84a17ee0b9583b45632b275` |
+
+The tag decodes as:
+
+- `0.0.1` — the version (from `VERSION`).
+- `20260724071739` — the build timestamp (`YYYYMMDDhhmmss`).
+- `adc5e7b97a6a52ace84a17ee0b9583b45632b275` — the git commit SHA the build was
+  produced from.
+
+## 3. Locate the artifacts in JFrog
+
+The promoted images resolve to artifacts in JFrog under the
+`proxy-deploy-releases-hyperspace-docker` repository. Browse them here:
+
+- <https://int.repositories.cloud.sap/ui/repos/tree/General/proxy-deploy-releases-hyperspace-docker>
+
+Navigate into the tree by image name and then the tag from the log line to find
+each promoted image:
+
+- `.../proxy-deploy-releases-hyperspace-docker/pipeline-fl-control-plane-engineering_agent`
+- `.../proxy-deploy-releases-hyperspace-docker/pipeline-fl-control-plane-fl_mcp_servers`
+- `.../proxy-deploy-releases-hyperspace-docker/pipeline-fl-control-plane`

```
