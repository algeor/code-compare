+## Architectural principles
+
+A few rules of thumb that shape every table below:
+
+1. **The DB is for what the runtime can't give us.** Kubernetes is the live source of truth for handler CRs and pod state; the **process engine** is the live source of truth for in-flight execution state, retries, and step transitions. The DB stores what those layers forget: history, audit trails, cross-component joins, and durable references.
+2. **HDLF is for raw pipeline data and produced output.** Logs, build artifacts, extracted metadata, handler/finalizer output payloads — anything large or stream-shaped — lives in HDLF. The DB only stores pointers (`path_to_hdlf` on `inspection`, `handler_executions`, `finalizer_execution`).
+3. **No speculative tables.** A table only exists when an owning component is being built that needs it. Future tables (`ci_instances`, `platform_config`) are deliberately deferred.
+4. **Audit-grade tables are append-only.** Failures, secret usage, feedback, telemetry are inserts; they don't get edited.
+5. **Secrets are referenced, never stored.** `audit_secrets_used` records names and Vault paths. The values themselves are always retrieved from Vault at runtime.
+6. **Execution orchestration is the process engine's job, not the DB's.** There is intentionally no `*_checkpoint` table, no DB-enforced state machine for internal stages, and no pod-ownership column on `inspection`. Liveness, retries, and step routing belong to the process engine; the DB only records terminal outcomes and audit trails.
+
+---
+
+## The central entity: `inspection`
+
+The DB is organized around the **inspection** — one execution of the FL platform's fault-detection pipeline against one CI run. Most other tables hang off `inspection`.
+
+```
+Pipeline triggers FL ──▶ Ingestion API
+                            │
+                            ▼
+                   INSERT inspection (status=ACCEPTED)
+                            │
+                            ▼
+                   Process engine drives execution:
+                     - dispatches handlers (INSERT handler_executions)
+                     - links handlers ↔ stages they address
+                       (INSERT handler_execution_failed_stages)
+                     - dispatches finalizers (INSERT finalizer_execution)
+                     - records produced output paths in HDLF
+                       (UPDATE *.path_to_hdlf)
+                     - records pipeline failures (INSERT failed_stages)
+                            │
+                            ▼
+                   On termination, process engine flips status:
+                     - ACCEPTED ─▶ IN_PROGRESS ─▶ COMPLETED
+                                              ╲▶ FAILED (and records inspection.error_message)
+                            │
+                            ▼
+                   UPDATE inspection.finished_at
+```
+
+The internal lifecycle (metadata extraction, pipeline analysis, data extraction, handler dispatch, etc.) is **not** modeled as a DB enum. Those are process-engine steps; their durable artifacts (failures, handler runs, finalizer runs) are individually captured by the tables below. **Handler and finalizer produced output is not stored in the DB — it lives in HDLF, referenced via `path_to_hdlf`.**
+

+## The tables
+
+### 1. `inspection`
+
+The lifecycle anchor. One row per FL invocation, created by the Ingestion API, terminating in `COMPLETED` or `FAILED`.
+
+**Owner:** Ingestion API (insert), process engine (status updates, terminal `error_message`)
+**Readers:** All components (most queries start here)
+
+#### Columns
+
+| Column | Type | Nullable | Description |
+|---|---|---|---|
+| `id` | VARCHAR(36) | NO (PK) | App-generated UUID4. Used as FK target by `handler_executions`, `failed_stages`, `finalizer_execution`. |
+| `status` | VARCHAR(32) | NO, default `ACCEPTED` | Lifecycle state. CHECK constrained to `ACCEPTED / IN_PROGRESS / COMPLETED / FAILED`. |
+| `pipeline_url` | VARCHAR(2048) | NO | URL of the originating CI pipeline run. Indexed for MCP / Admin UI lookup. |
+| `github_repo_url` | VARCHAR(2048) | YES | Source repo URL, distinct from `pipeline_url`. Indexed for repo-scoped queries. |
+| `repo_name` | VARCHAR(255) | YES | Short repo identifier (e.g. `Lenny/my-service`) — derived from `github_repo_url` but stored separately for cheap indexing and grouping. Indexed. |
+| `commit_id` | VARCHAR(2048) | YES | Git commit SHA the pipeline ran against. Useful for correlating with PR / branch state. |
+| `triggered_by` | VARCHAR(255) | YES | User or service principal that initiated the pipeline. Nullable for system-triggered runs. |
+| `path_to_hdlf` | VARCHAR(2048) | YES | URI pointing at this inspection's slot in HDLF (raw pipeline data, logs, extracted metadata). |
+| `error_message` | NCLOB | YES | Long-form operator-facing description of the **FL-internal** terminal error when `status='FAILED'`. Distinct from `failed_stages.error_message` (which describes failures of the **user pipeline being analyzed**). |
+| `created_at` | TIMESTAMP | NO | Insert time. Indexed for time-ordered listings. |
+| `updated_at` | TIMESTAMP | YES | Bumped on every status transition. Indexed for "recently active" Admin UI listings. |
+| `finished_at` | TIMESTAMP | YES | Set when the inspection terminates (`COMPLETED` or `FAILED`). Powers SLA reporting (`finished_at - created_at`). |
+
+#### State machine
+
+`status` is intentionally coarse — only the four high-level states the DB needs to know about:
+
+```
+ACCEPTED ──▶ IN_PROGRESS ──▶ COMPLETED
+                          ╲▶ FAILED   (set inspection.error_message, finished_at)
+```
+
+Internal step routing (metadata extraction, pipeline analysis, handler dispatch, finalizer execution) is owned by the **process engine**; the DB does not model it. Components do not advance `status` directly via predecessor-guarded UPDATEs anymore — the process engine flips it on terminal transitions only.
+
+#### Indexes
+
+- `pipeline_url` — MCP / Admin UI lookup by pipeline URL
+- `github_repo_url` — repo-scoped queries (Admin UI, repo-level reporting)
+- `repo_name` — short-form repo grouping for dashboards and FaultHandler `repo_patterns` matching
+- `created_at` — time-ordered listing
+- `updated_at` — recently-active listing
+
+#### Design decisions
+
+- **`id` is app-generated, not DB-assigned.** The Ingestion API generates a UUID4 before INSERT so the ID can be returned to the CI caller before any DB round-trip latency dominates.
+- **No pod / checkpoint columns.** Liveness and retry tracking belong to the process engine. Putting `pod_id` or `checkpoint_step` here would lie when ownership changes mid-flight.
+- **`error_message` captures FL-internal failures only.** Failures of the *user's CI pipeline* (the thing FL is analyzing) live in `failed_stages`. The two concerns are separated on purpose — `failed_stages` can have many rows per inspection, `inspection.error_message` is the single terminal "why did FL itself fail to complete this inspection" reason.
+- **`repo_name` is derived but stored.** The short form is what dashboards filter by; computing it from `github_repo_url` on every query is wasteful and the URL format may evolve over time.
+- **No internal-stage enum on `status`.** Earlier drafts proposed a 7-state enum (`METADATA_EXTRACTOR`, `PIPELINE_ANALYZER`, etc.). Dropped — those are process-engine steps, not DB states.
+

+### 2. `pipeline_analyzer_results`
+
+The Pipeline Analyzer's gating decision for an inspection. One row per analyzer run, recording whether the inspection should stop or continue, whether the finalizer should deliver a user-facing message, and (when the run was halted) which gate produced the stop decision. The full structured findings live in HDLF, referenced by `result_storage_path`.
+
+**Owner:** Pipeline Analyzer (insert once per run)
+**Readers:** Process engine (consumes `analysis_decision` to decide whether to continue the inspection), Finalizer dispatcher (reads `require_finalizer` and `message`), Admin UI
+
+#### Columns
+
+| Column | Type | Nullable | Description |
+|---|---|---|---|
+| `id` | VARCHAR(36) | NO (PK) | App-generated UUID4 |
+| `inspection_id` | VARCHAR(36) | NO (FK) | → `inspection(id)`. Not UNIQUE — multiple analyzer passes per inspection are permitted. |
+| `analysis_decision` | BOOLEAN | NO | `TRUE` = continue inspection; `FALSE` = stop. The process engine reads this to decide whether downstream steps run. |
+| `require_finalizer` | BOOLEAN | NO | `TRUE` = the finalizer should deliver `message` (or a derived user-facing payload) back to the pipeline. `FALSE` = no finalizer delivery needed for this analyzer outcome. |
+| `gate` | VARCHAR(63) | YES | Identifier of the gate that rejected the run, when one did. NULL when the analyzer did not stop the inspection. CHECK constrained to a closed set. |
+| `message` | VARCHAR(2048) | YES | Short-form reason / payload key (e.g. `wip_pr_detected`). NULL when no operator-facing message is required. |
+| `result_storage_path` | VARCHAR(2048) | YES | URI of the analyzer's full `findings.json` artifact in HDLF. NULL when no findings were produced. |
+| `created_at` | TIMESTAMP | NO | Insert time. Indexed for time-ordered queries. |
+
+#### Constraints
+
+- `gate IS NULL OR gate IN ('wip_detection')` — closed set; extend the CHECK as new gates ship.
+
+#### Indexes
+
+- `inspection_id` — primary query: "what did the analyzer decide for this inspection?"
+- `created_at` — time-ordered listings and recent-failure dashboards
+
+#### Design decisions
+
+- **Multiple results per inspection are allowed.** Re-runs (manual replay, retried analysis) each get their own row; consumers wanting "the latest decision" sort by `created_at DESC` and pick the head row. A UNIQUE on `inspection_id` was considered and rejected to keep replay flows append-only.
+- **`analysis_decision` is a BOOLEAN, not an enum.** The decision the engine cares about is binary (stop vs. continue); the *reason* it stopped lives in `gate` + `message`. Forcing this into a multi-valued enum would push reason information into the same column as the decision itself.
+- **`gate` is enumerated; `message` is free-form.** Aggregating "how often did `wip_detection` reject runs?" needs a closed set on `gate`. The customer-facing `message` (e.g. `wip_pr_detected`) is a payload key that may evolve faster than the gate vocabulary, so it's left free-form.
+- **Findings live in HDLF.** Same reasoning as `handler_executions.path_to_hdlf` and `finalizer_execution.path_to_hdlf` — variable-shape, potentially large output payloads belong outside the relational store. The DB only carries the pointer.
+- **`result_storage_path` is nullable.** Not every analyzer outcome produces a findings artifact (e.g. a fast-path WIP rejection may carry just a gate + message). Forcing NOT NULL would create artificial empty-file writes.
+

+### 3. `fault_handlers`
+
+The control plane's append-only mirror of HandlerCR Kubernetes resources. Populated by a watch loop in the Handler Orchestrator. Each CR revision gets a new row so `handler_executions` can FK to the exact revision that ran.
+
+**Owner:** Handler Orchestrator (k8s watch loop reconciliation)
+**Readers:** Handler Orchestrator (routing decisions), Admin UI
+
+#### Columns
+
+| Column | Type | Nullable | Description |
+|---|---|---|---|
+| `id` | VARCHAR(36) | NO (PK) | App-generated UUID4. Each CR revision gets a new row with a new `id`. |
+| `cr_id` | VARCHAR(253) | NO | k8s `metadata.uid` — stable across in-place updates. Indexed; multiple rows may share `cr_id`. |
+| `cr_name` | VARCHAR(253) | NO | k8s `metadata.name` |
+| `cr_namespace` | VARCHAR(253) | NO | k8s `metadata.namespace` |
+| `fault_id` | VARCHAR(253) | NO | Fault category this handler claims to handle. Indexed. |
+| `execution_type` | VARCHAR(20) | NO | CHECK: `agent_task` / `custom_runtime` |
+| `scope` | VARCHAR(20) | NO | CHECK: `stage_scoped` / `pipeline_scoped` |
+| `ci_systems` | VARCHAR(255) | YES | JSON array of CI system names this handler applies to (NULL = all) |
+| `repo_patterns` | VARCHAR(255) | YES | JSON array of repo URL patterns (NULL = all) |
+| `trigger_scope` | VARCHAR(20) | NO, default `'all'` | CHECK: `all` / `pr_only` / `non_pr_only` |
+| `merge_target_branch` | VARCHAR(255) | YES | Restrict to PRs targeting this branch (NULL = all branches) |
+| `spec_json` | NCLOB | YES | Full CR spec snapshot — for audit / replay |
+| `resource_version` | VARCHAR(253) | NO | k8s optimistic concurrency token. Required (NOT NULL) so every row is anchored to a specific cluster revision. |
+| `last_patched_phase` | VARCHAR(20) | YES | Phase of the most recent server-side patch the orchestrator applied to the CR (e.g. when annotating status, retry counters). NULL if the orchestrator has never patched this row. Free-form — no CHECK enum. |
+| `is_active` | BOOLEAN | NO, default TRUE | Soft-delete flag |
+| `registered_at` | TIMESTAMP | NO | When this CR first appeared in the cluster |
+| `updated_at` | TIMESTAMP | YES | When the row was last reconciled from k8s |
+
+#### Constraints
+
+- `execution_type IN ('agent_task', 'custom_runtime')`
+- `scope IN ('stage_scoped', 'pipeline_scoped')`
+- `trigger_scope IN ('all', 'pr_only', 'non_pr_only')`
+
+#### Indexes
+
+- `cr_id` — lookup all revisions of a given CR
+- `fault_id` — primary access pattern: "which handlers exist for this fault category?"
+
+#### Design decisions
+
+- **Append-only registry; `id` is the PK, `cr_id` is just an indexed column.** k8s `metadata.uid` stays stable across in-place CR updates, which would collapse multiple revisions into one row if used as PK. A new `id` per row preserves full version history.
+- **`handler_executions` references the exact `fault_handlers.id` that was active at dispatch time** — preserving the audit trail even if the CR is later edited or deleted.
+- **Soft delete via `is_active`, not row deletion.** When a HandlerCR is deleted in k8s, the latest row is marked `is_active=FALSE`; old `handler_executions` still resolve.
+- **`spec_json` is a snapshot for audit, not for routing.** Routing reads denormalized columns (`fault_id`, `execution_type`, etc.).
+- **`resource_version` is NOT NULL.** Every row must be anchored to a specific cluster revision; without it, the orchestrator can't reason about whether a CR has drifted between reads. The watcher always has a `resourceVersion` to record, so requiring it costs nothing.
+- **`last_patched_phase` is free-form.** It records *which orchestrator phase* most recently issued a server-side patch against the CR (status annotation, retry counter bump, etc.). Different deployments may add new phases without a schema migration; a CHECK enum would be over-constraint here.
+- **Live source of truth is Kubernetes.** This table is a cache. If it goes out of sync, the watcher rebuilds it.
+

+### 4. `controller_status`
+
+Singleton row capturing the Handler Orchestrator's last reconciliation cycle. Exactly one row exists, enforced at the DB layer by `CHECK (id = 1)` on the primary key — consumers can read controller health with a fixed-PK lookup (`SELECT … WHERE id = 1`) and never need to handle "row missing" or "many rows" cases at runtime.
+
+**Owner:** Handler Orchestrator (writes after each reconciliation cycle)
+**Readers:** Admin UI, alerting / health checks, orchestrator self-introspection
+
+#### Columns
+
+| Column | Type | Nullable | Description |
+|---|---|---|---|
+| `id` | INTEGER | NO (PK) | Always `1`. CHECK constraint enforces single-row semantics. |
+| `last_sync_time` | TIMESTAMP | YES | Wall-clock time of the most recent reconciliation cycle. NULL before the first sync. |
+| `sync_duration_ms` | INTEGER | YES | Duration of the most recent reconciliation cycle, in milliseconds. NULL before the first sync. |
+| `handlers_active` | INTEGER | NO, default 0 | Count of `fault_handlers` rows currently `is_active=TRUE` after the last sync. |
+| `handlers_inactive` | INTEGER | NO, default 0 | Count of `fault_handlers` rows currently `is_active=FALSE` after the last sync (soft-deleted, retired). |
+| `handlers_error` | INTEGER | NO, default 0 | Count of HandlerCRs that errored during reconciliation in the last sync (couldn't parse, k8s API rejected the patch, etc.). |
+| `circuit_breaker_active` | BOOLEAN | NO, default FALSE | TRUE when the orchestrator has tripped its circuit breaker (e.g. too many sync failures in a row) and is refusing further reconciliation cycles until reset. |
+| `updated_at` | TIMESTAMP | YES | When the row was last written. NULL before the first sync. |
+
+#### Constraints
+
+- `CHECK (id = 1)` — enforces exactly one row in the table
+
+#### Indexes
+
+None — single-row table; the PK is the only access path needed.
+
+#### Design decisions
+
+- **Singleton via CHECK, not application convention.** The DB enforces "there is exactly one row" so multi-instance orchestrators can't accidentally write multiple status rows during a leader-election handoff. The first writer creates `id=1`; subsequent writers `UPDATE` it.
+- **No history.** This table records *current state*, not a time series. If you need historical sync metrics, they belong in Prometheus / OpenTelemetry, not in the DB. The architectural principle "the DB is for what the runtime can't give us" applies — Prometheus is the right place for liveness/duration history.
+- **Counters are post-sync snapshots.** `handlers_active / inactive / error` are written at the end of each reconciliation cycle. They reflect the state of `fault_handlers` immediately after the sync completed; queries reading both `controller_status` and `fault_handlers` may see slight skew if a subsequent CR change has landed since the sync.
+- **`circuit_breaker_active` is durable.** When the orchestrator restarts, it reads `circuit_breaker_active` to decide whether to resume reconciliation or stay paused. Storing this in the DB rather than in process memory means a crash-loop doesn't accidentally clear the breaker.
+

+### 5. `handler_executions`
+
+The audit trail of every handler run. One row per "we attempted to run handler X for inspection Y," persisted forever (long after the k8s Job that ran it has been GC'd).
+
+**Owner:** Handler Orchestrator (insert with `status=planned`), Execution Engine / Agent Task Runtime (status updates, `path_to_hdlf` on success)
+**Readers:** Result Collector, Admin UI
+
+#### Columns
+
+| Column | Type | Nullable | Description |
+|---|---|---|---|
+| `id` | VARCHAR(36) | NO (PK) | UUID4 |
+| `inspection_id` | VARCHAR(36) | NO (FK) | → `inspection(id)` |
+| `fault_handler_id` | VARCHAR(36) | NO (FK) | → `fault_handlers(id)` — exact handler revision that ran |
+| `fault_id` | VARCHAR(255) | NO | Fault category this execution was dispatched for |
+| `status` | VARCHAR(20) | NO | One of: `planned`, `running`, `success`, `failed`, `timed_out` |
+| `status_message` | VARCHAR(100) | YES | Free text giving operator context for the current status (e.g. why it failed). |
+| `path_to_hdlf` | VARCHAR(2048) | YES | URI pointing at this execution's output payload in HDLF. Set when the runtime stores produced output. |
+| `created_at` | TIMESTAMP | NO | When the execution was planned |
+| `updated_at` | TIMESTAMP | YES | Bumped on every status transition |
+| `finished_at` | TIMESTAMP | YES | Set when status reaches a terminal value |
+
+#### Status enum semantics
+
+| Status | Meaning |
+|---|---|
+| `planned` | Orchestrator has decided to run this handler; runtime hasn't started yet |
+| `running` | Runtime is actively executing |
+| `success` | Handler completed and produced output (the runtime stored the payload at `path_to_hdlf`) |
+| `failed` | Handler ran but errored out |
+| `timed_out` | Handler exceeded its deadline |
+
+#### Indexes
+
+- `(inspection_id, fault_id)` — primary access pattern
+- `status` — operator queries
+
+#### Design decisions
+
+- **One row per attempt, not per retry.** A failed execution that gets retried produces a new `handler_executions` row. Each row's status advances monotonically toward a terminal state.
+- **No k8s Job / Pod columns.** `agent_task` runs on the Agent Task Runtime (no Job created); `custom_runtime` spawns a k8s Job. Either-or columns would be NULL for half the rows. Live runtime status is read through to k8s on demand.
+- **Output lives in HDLF, not in the DB.** Earlier drafts had an `inspection_results` table holding `critical_error / explanation / fix_suggestion / diff` columns. That was removed — handler output shapes vary too widely for a fixed tuple, and large NCLOB rows belong outside the relational store. `path_to_hdlf` is the durable pointer.
+- **Stage linkage is M:N via `handler_execution_failed_stages`** — a handler may address multiple stages (or zero, for pipeline-scoped handlers); a stage may be addressed by multiple handlers.
+- **`status_message` replaces the earlier `skip_reason` column.** Generic enough to carry operator context for any non-running state.
+

+### 6. `audit_secrets_used`
+
+Compliance-grade record of every secret that was *referenced* during a handler execution. Stores names and Vault paths only — **never values**.
+
+**Owner:** Execution Engine / Agent Task Runtime (whichever resolves the secret at runtime)
+**Readers:** Admin UI, compliance / audit tooling
+
+#### Columns
+
+| Column | Type | Nullable | Description |
+|---|---|---|---|
+| `id` | VARCHAR(36) | NO (PK) | UUID4 |
+| `execution_id` | VARCHAR(36) | NO (FK) | → `handler_executions(id)` |
+| `secret_name` | VARCHAR(255) | NO | Logical name (e.g., `github-read-token`, `piper-api-key`) |
+| `resolution_source` | VARCHAR(20) | NO | CHECK: `pipeline` / `platform` / `unavailable` |
+| `secret_path` | VARCHAR(2048) | YES | Full Vault path. NULL when `resolution_source='unavailable'`. |
+
+#### `resolution_source` semantics
+
+| Value | Meaning |
+|---|---|
+| `pipeline` | Secret was provided by the pipeline being analyzed (CI-scoped credential) |
+| `platform` | Secret came from FL's own credential store (platform-owned) |
+| `unavailable` | Handler asked for the secret but it couldn't be resolved |
+
+#### Indexes
+
+None. Access is always via the FK from `handler_executions` — operator and audit queries start from a known `handler_executions.id` and join to this table. No standalone scan-by-`secret_name` access pattern exists today; if one emerges (e.g. "show every handler that requested the github token"), an `ix_audit_secrets_used_secret_name` index can be added at that time.
+
+#### Design decisions
+
+- **Names and paths only — no values.** Storing the value would be the security problem this table is meant to prevent.
+- **`resolution_source` makes the trust boundary visible.** Auditors can answer "did any handler pull production-DB credentials from the platform vault last quarter?" with one query.
+- **`unavailable` rows are intentional.** They record "handler tried to use this secret and couldn't" — useful for debugging skipped runs and detecting handlers that are silently failing.
+- **No FK to a `secrets` table.** There isn't one. Vault is the source of truth.
+

+### 7. `failed_stages`
+
+Append-only log of failures of the **user's CI pipeline** — the pipeline being analyzed by FL. Decoupled from `inspection` because a single inspection can record multiple failed stages.
+
+**Owner:** Whichever component / process-engine step records the failure
+**Readers:** Admin UI, retry / debug tooling, handler routing
+
+#### Columns
+
+| Column | Type | Nullable | Description |
+|---|---|---|---|
+| `id` | VARCHAR(36) | NO (PK) | App-generated UUID4 |
+| `inspection_id` | VARCHAR(36) | NO (FK) | → `inspection(id)` |
+| `stage_name` | VARCHAR(255) | NO | Free-form name of the **CI/user pipeline stage** that failed (e.g. `mavenExecuteStaticCodeChecks`, `npmExecuteScripts`, `deploy`). |
+| `error_message` | NCLOB | YES | Operator-facing error context. Long form. |
+| `created_at` | TIMESTAMP | NO | When the failure occurred |
+
+#### Indexes
+
+- `(inspection_id, created_at)` — primary query: "show me the failure history for this inspection"
+- `(stage_name, created_at)` — operator reporting: "where are pipelines failing most?"
+
+#### Design decisions
+
+- **1 : N with `inspection`** — an inspection can have multiple failed stages.
+- **Decoupled from `inspection`** so the inspection row stays terse and a chronological audit log of user-pipeline failures can be queried independently.
+- **Distinct from `inspection.error_message`.** This table records failures of the *pipeline being analyzed*; `inspection.error_message` records failures of *FL itself*. Don't conflate them.
+- **`stage_name` is free-form (no CHECK enum).** Stage names come from arbitrary CI systems (Jenkins, Piper, GitHub Actions, etc.) and the set is unbounded. Earlier drafts constrained `stage_name` to an internal enum — that was wrong; the column captures *the failed stage in the pipeline being analyzed*, not an internal control-plane step.
+- **Core fields only.** Stack trace, error code, retry counter, pod / request correlation — all deliberately deferred.
+

+### 8. `handler_execution_failed_stages`
+
+Many-to-many junction linking which **handler executions** addressed which **failed stages** of the user pipeline. Captures the routing decision the orchestrator made at dispatch time.
+
+**Owner:** Handler Orchestrator (insert at dispatch time)
+**Readers:** Admin UI ("which handler ran for which failure?"), debug / replay tooling
+
+#### Columns
+
+| Column | Type | Nullable | Description |
+|---|---|---|---|
+| `handler_execution_id` | VARCHAR(36) | NO (PK, FK) | → `handler_executions(id)` |
+| `failed_stage_id` | VARCHAR(36) | NO (PK, FK) | → `failed_stages(id)` |
+
+The composite `(handler_execution_id, failed_stage_id)` is the primary key — there is no separate surrogate `id`.
+
+#### Indexes
+
+- Implicit index on `(handler_execution_id, failed_stage_id)` from the composite PK — covers `WHERE handler_execution_id = ?` lookups
+- Explicit index on `failed_stage_id` — covers reverse lookups ("which handlers were dispatched for this stage?")
+
+#### Design decisions
+
+- **M:N, not 1:N** — pipeline-scoped handlers may address multiple failed stages; a single failed stage may trigger multiple handlers (different `fault_id`s targeting the same failure). Either direction needs to be queryable.
+- **No rows for pipeline-scoped handlers that don't bind to a specific stage.** A handler with `scope='pipeline_scoped'` is dispatched against the inspection as a whole; absence of rows here is the signal that this handler isn't stage-bound.
+- **No surrogate PK.** A junction table doesn't need one — the composite PK is the natural key, and the table is purely associative (no per-row attributes that other tables FK to).
+- **No timestamps.** The dispatch time is implied by `handler_executions.created_at`; storing it again would invite drift.
+

+### 9. `handler_agent_telemetry`
+
+Token-usage record for `agent_task` handler runs (Cline / LLM-driven). One row per handler execution that involved the agent runtime; `custom_runtime` executions don't produce rows here.
+
+**Owner:** Agent Task Runtime
+**Readers:** Admin UI, cost / usage analytics
+
+#### Columns
+
+| Column | Type | Nullable | Description |
+|---|---|---|---|
+| `id` | VARCHAR(36) | NO (PK) | UUID4 |
+| `execution_id` | VARCHAR(36) | NO (FK, UNIQUE) | → `handler_executions(id)`. UNIQUE enforces 0..1:1. |
+| `input_tokens` | INTEGER | NO, default 0 | Tokens sent to the model |
+| `output_tokens` | INTEGER | NO, default 0 | Tokens returned by the model |
+| `total_tokens` | INTEGER | NO, default 0 | Denormalized sum (= input + output) |
+| `model_name` | VARCHAR(100) | NO | Model identifier (e.g., `claude-opus-4-6`) |
+| `created_at` | TIMESTAMP | NO | Insert time |
+
+#### Indexes
+
+- `(model_name, created_at)` — aggregate token usage per model over time
+- (Implicit index on `execution_id` from the UNIQUE constraint covers join-back lookups; no separate index declared.)
+
+#### Design decisions
+
+- **0..1 : 1 with `handler_executions`** — only `agent_task` runs produce telemetry rows. UNIQUE on `execution_id` enforces this.
+- **Token-only scope.** Cost, cache tokens, latency, provider IDs, and tool-call counters are deferred.
+- **`total_tokens` is denormalized for fast aggregation.** Writer keeps it consistent with `input_tokens + output_tokens`.
+
+---
+
+### 10. `finalizer_registry`
+
+Static catalog of finalizer definitions. A *finalizer* describes WHAT runs for a given step in the FL pipeline (prompt, skills, MCPs, etc.). `finalizer_execution` rows reference an entry here by registry id.
+
+**Owner:** Whatever bootstraps / registers finalizers (operator tooling, deployment manifests)
+**Readers:** Process engine (looks up the definition before dispatch), Admin UI
+
+#### Columns
+
+| Column | Type | Nullable | Description |
+|---|---|---|---|
+| `id` | VARCHAR(36) | NO (PK) | App-generated UUID4 |
+| `finalizer_id` | VARCHAR(255) | NO | Logical identifier (e.g. `pipeline_analyzer`, `metadata_extractor`) |
+| `finalizer_version` | VARCHAR(63) | NO | Version string |
+| `display_name` | VARCHAR(255) | YES | Human-readable name for Admin UI |
+| `description` | NCLOB | YES | Free-text description of what this finalizer does |
+| `execution_type` | VARCHAR(20) | NO | CHECK: `agent_task` / `custom_runtime` |
+| `prompt` | NCLOB | YES | Prompt text. Required when `execution_type='agent_task'` (enforced by CHECK). |
+| `skills_json` | NCLOB | YES | JSON array of skill identifiers the finalizer uses |
+| `mcps_json` | NCLOB | YES | JSON array of MCP server identifiers the finalizer uses |
+| `is_active` | BOOLEAN | NO, default TRUE | Soft-delete flag |
+| `registered_at` | TIMESTAMP | NO | When this version was registered |
+| `updated_at` | TIMESTAMP | YES | Last-updated timestamp |
+
+#### Constraints
+
+- `UNIQUE (finalizer_id, finalizer_version)` — each version appears at most once
+- `execution_type IN ('agent_task', 'custom_runtime')`
+- `execution_type <> 'agent_task' OR prompt IS NOT NULL` — agent_task finalizers must define a prompt; custom_runtime finalizers describe behaviour via spec rather than prompt, so prompt is optional there.
+
+#### Indexes
+
+- `finalizer_id` — lookup all versions of a given finalizer
+
+#### Design decisions
+
+- **Versioned and append-only at the (id, version) granularity.** A new finalizer version is a new row; older versions stay queryable for audit.
+- **Prompt nullable, conditionally required.** The CHECK enforces that `agent_task` finalizers always carry a prompt without forcing one onto `custom_runtime` rows.
+- **JSON columns for skills/mcps.** The set of skills and MCPs is open and the schema doesn't need to enforce structure on them. JSON text fits HANA NCLOB cleanly.
+
+---
+
+### 11. `finalizer_execution`
+
+One row per finalizer invocation — the audit record linking an `inspection` to the exact `finalizer_registry` entry that ran. Carries the same status lifecycle as `handler_executions`, plus a pointer to the produced output in HDLF.
+
+**Owner:** Process engine (insert at dispatch with `status=planned`, status updates and `path_to_hdlf` as the run progresses)
+**Readers:** Admin UI, analytics, Result Collector, feedback aggregation
+
+#### Columns
+
+| Column | Type | Nullable | Description |
+|---|---|---|---|
+| `id` | VARCHAR(36) | NO (PK) | UUID4 |
+| `inspection_id` | VARCHAR(36) | NO (FK) | → `inspection(id)` |
+| `finalizer_registry_id` | VARCHAR(36) | NO (FK) | → `finalizer_registry(id)` — exact version that ran |
+| `is_active` | BOOLEAN | NO, default TRUE | Soft-delete flag |
+| `status` | VARCHAR(20) | NO, default `planned` | Lifecycle state. CHECK: `planned / running / success / failed / timed_out` (same enum as `handler_executions.status`). |
+| `status_message` | VARCHAR(100) | YES | Free text giving operator context for the current status. |
+| `path_to_hdlf` | VARCHAR(2048) | YES | URI pointing at this finalizer run's output payload in HDLF. Set on `success`. |
+| `created_at` | TIMESTAMP | NO | Insert time |
+| `updated_at` | TIMESTAMP | YES | Bumped on every status transition |
+| `finished_at` | TIMESTAMP | YES | Set when status reaches a terminal value |
+
+#### Indexes
+
+- `inspection_id` — primary query: "which finalizers ran for this inspection?"
+- `finalizer_registry_id` — reverse lookup: "where has this finalizer version run?"
+
+#### Design decisions
+
+- **Status lifecycle mirrors `handler_executions`.** Finalizers and handlers have the same operational shape (dispatch → run → terminal state); using the same enum keeps the mental model consistent across both audit trails.
+- **Output in HDLF, not in the DB.** Same reasoning as `handler_executions.path_to_hdlf` — finalizer output shapes are open-ended and large; the relational store carries the pointer, not the payload.
+- **`finalizer_registry_id` is NOT NULL.** Every dispatched finalizer must reference a registry entry — there is no anonymous finalizer run.
+- **`is_active` is independent of `status`.** `is_active=FALSE` is an admin / operator action (retire a misconfigured run); `status='failed'` is what the runtime reports. They mean different things.
+

+### 12. `feedback`
+
+Developer feedback on a finalizer run's output — was the analysis useful, was the fix correct, was this a false positive? Aggregated for both Admin UI dashboards and downstream training pipelines.
+
+**Owner:** Feedback API (insert) — also receives writes from Admin UI, MCP server, and PR Monitor (all going through the API)
+**Readers:** Admin UI, training / analytics pipelines
+
+#### Columns
+
+| Column | Type | Nullable | Description |
+|---|---|---|---|
+| `id` | VARCHAR(36) | NO (PK) | UUID4 |
+| `finalizer_execution_id` | VARCHAR(36) | NO (FK) | → `finalizer_execution(id)` — feedback always anchors to a specific finalizer run |
+| `source` | VARCHAR(20) | NO | CHECK: `api` / `ui` / `mcp` / `pr_monitor` |
+| `assessment` | VARCHAR(20) | NO | CHECK: `helpful` / `not_helpful` / `false_positive` / `correct_fix` / `wrong_fix` |
+| `comment` | NCLOB | YES | Free-text "why" — the qualitative signal |
+| `created_at` | TIMESTAMP | NO | Insert time |
+
+#### `source` channels
+
+| Value | Origin |
+|---|---|
+| `api` | Direct API call (programmatic feedback) |
+| `ui` | Admin UI thumbs-up/down |
+| `mcp` | Feedback submitted through the FL MCP server |
+| `pr_monitor` | Implicit feedback from PR signals — e.g., the suggested diff was merged or reverted |
+
+#### Indexes
+
+- `finalizer_execution_id` — primary query: "show me all feedback for this finalizer run"
+- `(source, created_at)` — channel-level reporting
+
+#### Design decisions
+
+- **Linked directly to `finalizer_execution`, not to a per-suggestion result row.** Earlier drafts had a separate `inspection_results` table with per-fault granularity; feedback FK'd into that. With output now stored in HDLF (not the DB), the relational anchor for feedback is the finalizer run itself. Per-fault granularity, if needed, lives in the HDLF payload that consumers can render alongside the feedback.
+- **`finalizer_execution_id` is NOT NULL.** Feedback that doesn't reference a specific finalizer run is meaningless — there's nothing to aggregate against.
+- **`assessment` is enumerated.** Aggregation across thousands of feedback rows requires a closed set; the free-form "why" lives in `comment`.
+- **No `submitted_by` column.** The Feedback API is responsible for stamping author identity into `comment` or via a separate auth-context table when one lands.

+## Conventions
+
+- **Primary keys are app-generated UUID4 strings** (`VARCHAR(36)`) unless otherwise noted, allowing IDs to be created before any DB round-trip. Junction tables (e.g. `handler_execution_failed_stages`) use composite PKs over the FK columns instead — no surrogate ID.
+- **Timestamps are UTC.** No `TIMESTAMP WITH TIME ZONE` — all writes use UTC, all reads assume UTC.
+- **CHECK constraints enforce enums at the DB layer** rather than only in component code.
+- **Foreign keys are declared and enforced.** No "soft" references via string IDs that the DB doesn't know about. SQLite requires `PRAGMA foreign_keys=ON` per connection (set by the application's SQLAlchemy `on_connect` event).
+- **Indexes follow the access pattern, not the data shape.** Every index in the schema corresponds to a documented query.
+- **Soft delete (via `is_active`) is preferred over hard DELETE** for any row that other tables FK to.
+- **Produced output goes to HDLF, not the DB.** Handlers and finalizers write payloads to object storage; the DB stores `path_to_hdlf` pointers. This applies to `inspection`, `handler_executions`, and `finalizer_execution`.
+- **Table creation order in `schema.sql` is significant for HANA.** Every referenced table is defined before any FK targets it. The order is documented in the header comment of `schema.sql`.
